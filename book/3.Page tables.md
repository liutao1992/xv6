### **页表（Page tables）**

**Page tables are the most popular mechanism through which the operating system provides each process with its own private address space and memory.**
页表是操作系统最常用的机制，用来为每个进程提供独立的私有地址空间和内存。

**Page tables determine what memory addresses mean, and what parts of physical memory can be accessed.**
页表决定了内存地址的含义，以及进程能访问物理内存的哪些部分。

**They allow xv6 to isolate different process’s address spaces and to multiplex them onto a single physical memory.**
它们使 xv6 能够隔离不同进程的地址空间，同时把它们复用到同一片物理内存上。

**Page tables are a popular design because they provide a level of indirection that allow operating systems to perform many tricks.**
页表之所以流行，是因为它提供了一层间接性，使操作系统能够实现许多“巧妙手段”。

**Xv6 performs a few tricks: mapping the same memory (a trampoline page) in several address spaces, and guarding kernel and user stacks with an unmapped page.**
例如，xv6 使用一些小技巧：

* 把同一块内存（比如 trampoline 页）映射到多个地址空间中；
* 使用未映射页来保护内核栈和用户栈。

**The rest of this chapter explains the page tables that the RISC-V hardware provides and how xv6 uses them.**
本章接下来会介绍 RISC-V 硬件提供的页表，以及 xv6 是如何使用它们的。

---

### **3.1 分页硬件（Paging hardware）**

**As a reminder, RISC-V instructions (both user and kernel) manipulate virtual addresses. The machine’s RAM, or physical memory, is indexed with physical addresses. The RISC-V page table hardware connects these two kinds of addresses, by mapping each virtual address to a physical address.**
提醒一下：无论是用户态还是内核态的 RISC-V 指令，都操作的是虚拟地址。而机器的 RAM（物理内存）使用物理地址索引。RISC-V 的页表硬件负责把虚拟地址映射到物理地址，从而连接二者。

---

**Xv6 runs on Sv39 RISC-V, which means that only the bottom 39 bits of a 64-bit virtual address are used; the top 25 bits are not used.**
xv6 运行在 **Sv39 RISC-V** 模式下，这意味着 64 位虚拟地址只有低 39 位被使用，高 25 位被忽略。

![图 3.1 分页硬件的工作原理](./img/截屏2025-08-24%2016.57.54.png)

**In this Sv39 configuration, a RISC-V page table is logically an array of 2²⁷ (134,217,728) page table entries (PTEs). Each PTE contains a 44-bit physical page number (PPN) and some flags.**
在 Sv39 配置下，RISC-V 页表逻辑上是一个 **2²⁷（1.34 亿）个条目** 的数组。每个条目（PTE）包含一个 **44 位物理页号（PPN）** 和一些标志位。

**The paging hardware translates a virtual address by using the top 27 bits of the 39 bits to index into the page table to find a PTE, and making a 56-bit physical address whose top 44 bits come from the PPN in the PTE and whose bottom 12 bits are copied from the original virtual address.**
分页硬件在翻译虚拟地址时，会用虚拟地址的高 27 位来索引页表，找到对应的 PTE；然后生成一个 56 位物理地址：高 44 位来自 PTE 中的物理页号，低 12 位直接复制虚拟地址的低 12 位。

**A page table gives the operating system control over virtual-to-physical address translations at the granularity of aligned chunks of 4096 (2¹²) bytes. Such a chunk is called a page.**
页表以 **4096 字节（2¹²）对齐的块** 为粒度，控制虚拟地址到物理地址的映射。这种块称为 **页（page）**。

---

> 什么是 PTE？

PTE（页表项） 是 页表（Page Table）中的一个元素。

页表是用来把 虚拟地址 (VA) 转换成 物理地址 (PA) 的。

每个 PTE 描述了一页（通常是 4KB）的映射信息，包括它在物理内存中的位置和访问权限。

> 什么是 PPN?

PPN 是 物理页号，是页表项 (PTE) 里最重要的部分。

它指明了 虚拟页 被映射到的 物理页帧 (Physical Frame)。

PPN 并不是完整的物理地址，而是物理地址的高位部分。

物理地址 = PPN + 页内偏移 (Page Offset)。

---

**As Figure 3.2 shows, a RISC-V CPU translates a virtual address into a physical in three steps. A page table is stored in physical memory as a three-level tree.**

如图 3.2 所示，RISC-V CPU 通过三步把虚拟地址转换成物理地址。页表存储在物理内存中，以一棵三层树的形式组织。

![图 3.2 分页硬件的工作原理](./img/截屏2025-08-24%2016.50.12.png)

> 这张图片展示了RISC-V架构中Sv39（39位虚拟地址）的完整三级页表地址转换过程

#### RISC-V Sv39三级页表地址转换机制详解

这张图片展示了RISC-V架构中Sv39（39位虚拟地址）的完整三级页表地址转换过程。

##### 1. 虚拟地址结构（39位有效地址）

```
64位虚拟地址: [EXT][L2][L1][L0][Offset]
               |   9  9  9    12位
               |
               └── 扩展位（符号扩展到64位）
```

- **EXT**：扩展位，将39位地址扩展到64位
- **L2**：二级页表索引（9位，512个条目）
- **L1**：一级页表索引（9位，512个条目）
- **L0**：零级页表索引（9位，512个条目）
- **Offset**：页内偏移（12位，4KB页面）

##### 2. 三级页表遍历过程

###### **第一步：根页表查找（L2级）**
1. 从**satp寄存器**获取根页表的物理基地址
2. 使用虚拟地址的**L2字段**（9位）作为索引
3. 在根页表中查找对应的页表项（PTE）
4. 获取下一级页表的物理页号（PPN）

###### **第二步：中间页表查找（L1级）**
1. 使用第一步获得的PPN构造L1级页表的物理地址
2. 使用虚拟地址的**L1字段**作为索引
3. 在L1级页表中查找对应的PTE
4. 获取下一级页表的PPN

###### **第三步：叶子页表查找（L0级）**
1. 使用第二步获得的PPN构造L0级页表的物理地址
2. 使用虚拟地址的**L0字段**作为索引
3. 在L0级页表中查找对应的PTE
4. 获取最终物理页面的PPN

###### **第四步：物理地址生成**
```
物理地址 = [最终PPN][虚拟地址的Offset]
           44位      12位
```

##### 3. 页表项（PTE）结构

每个页表项包含：
- **PPN（44位）**：指向下一级页表或最终物理页面的物理页号
- **Flags（10位）**：控制位，包括：
  - V（Valid）：有效位
  - R（Read）：读权限
  - W（Write）：写权限
  - X（Execute）：执行权限
  - U（User）：用户态访问权限
  - G（Global）：全局页面标志
  - A（Accessed）：访问位
  - D（Dirty）：脏位
  - RSW：保留位

##### 4. satp寄存器的作用

**satp（Supervisor Address Translation and Protection）寄存器**：
- 存储根页表的物理基地址
- 控制地址转换模式
- 包含地址空间标识符（ASID）

##### 5. 设计优势

###### **内存效率**
- **按需分配**：只为实际使用的虚拟地址区域分配页表
- **稀疏地址空间支持**：大部分未使用的地址空间不占用物理内存

###### **性能优化**
- **TLB友好**：每级9位索引，页表大小为4KB，与页面大小匹配
- **缓存局部性**：页表访问具有良好的空间局部性

###### **可扩展性**
- **统一结构**：每级页表结构相同，便于硬件实现
- **灵活映射**：支持大页面（通过在中间级别设置叶子页表项）

##### 6. 地址空间计算

```
虚拟地址空间 = 2^39 = 512GB
物理地址空间 = 2^56 = 64PB（理论上）
页表项数量 = 512 × 512 × 512 = 134,217,728（最大）
实际使用 = 按需分配，通常远小于最大值
```

##### 7. 与单级页表的对比

| 特性 | 单级页表 | 三级页表 |
|------|----------|----------|
| 页表大小 | 固定大量内存 | 按需分配 |
| 内存开销 | 高 | 低（稀疏地址空间） |
| 访问延迟 | 1次内存访问 | 3次内存访问 |
| TLB重要性 | 一般 | 非常重要 |

这种三级页表设计是现代虚拟内存系统的标准实现，在内存效率和访问性能之间达到了良好的平衡，特别适合现代应用程序的内存使用模式。

---

**The root of the tree is a 4096-byte page-table page that contains 512 PTEs, which contain the physical addresses for page-table pages in the next level of the tree. Each of those pages contains 512 PTEs for the final level in the tree.**
树的根节点是一个 **4096 字节的页表页**，里面有 512 个 PTE，每个 PTE 指向下一层的页表页。每个中间页表页又有 512 个 PTE，指向最终的页表页。

**The paging hardware uses the top 9 bits of the 27 bits to select a PTE in the root, the middle 9 bits to select a PTE in the next level, and the bottom 9 bits to select the final PTE.**
分页硬件会用这 27 位中的：

* **最高 9 位** 选择根页表中的一个 PTE；
* **中间 9 位** 选择下一层页表中的一个 PTE；
* **最低 9 位** 选择最终页表中的 PTE。

**If any of the three PTEs required to translate an address is not present, the paging hardware raises a page-fault exception, leaving it up to the kernel to handle.**
如果转换过程中需要的三个 PTE 有任意一个不存在，分页硬件会触发 **缺页异常（page fault）**，交由内核处理。

---

**To avoid the cost of loading PTEs from physical memory, a RISC-V CPU caches page table entries in a Translation Look-aside Buffer (TLB).**
为了避免每次都从物理内存加载 PTE，RISC-V CPU 会使用 **TLB（快表）** 缓存页表项。

**Each PTE contains flag bits that tell the paging hardware how the associated virtual address is allowed to be used:**
每个 PTE 中都有标志位，告诉分页硬件该虚拟地址的使用方式：

* `PTE_V`：该 PTE 是否有效。如果无效，访问会触发异常。
* `PTE_R`：是否允许读取该页。
* `PTE_W`：是否允许写入该页。
* `PTE_X`：是否允许把该页的内容当作指令执行。
* `PTE_U`：用户态是否允许访问该页；如果没设置，则只能在内核态访问。

这些标志以及其他相关定义在 `kernel/riscv.h` 中。

---

**To tell a CPU to use a page table, the kernel must write the physical address of the root page-table page into the `satp` register.**
要让 CPU 使用某个页表，内核必须把页表根页的物理地址写入 `satp` 寄存器。

**Each CPU has its own satp so that different CPUs can run different processes, each with a private address space described by its own page table.**
每个 CPU 都有自己的 `satp`，这样不同的 CPU 可以运行不同的进程，每个进程都有自己独立的地址空间。

---
**From the kernel’s point of view, a page table is data stored in memory, and the kernel creates and modifies page tables using code much like you might see for any tree-shaped data structure.**
从内核的角度来看，页表就是存储在内存中的数据，而内核通过类似于处理树形数据结构的代码来创建和修改页表。

**A few notes about terms used in this book. Physical memory refers to storage cells in RAM.**
这里对本书中使用的一些术语作一些说明。**物理内存（Physical memory）** 指的是 **RAM 中的存储单元**。

**A byte of physical memory has an address, called a physical address.**
物理内存中的每一个字节都有一个地址，这个地址称为 **物理地址（Physical address）**。

**Instructions that dereference addresses (such as loads, stores, jumps, and function calls) use only virtual addresses, which the paging hardware translates to physical addresses, and then sends to the RAM hardware to read or write storage.**
所有涉及解引用地址的指令（例如 **加载 load**、**存储 store**、**跳转 jump**、**函数调用 function call**）只使用 **虚拟地址**。分页硬件会将虚拟地址转换为物理地址，然后把物理地址交给 RAM 硬件去执行读写操作。

**An address space is the set of virtual addresses that are valid in a given page table;**
**地址空间（Address space）** 指的是某个给定页表中有效的虚拟地址集合。


**each xv6 process has a separate user address space, and the xv6 kernel has its own address space as well.**
每一个 xv6 进程都有自己独立的 **用户地址空间**，同时 xv6 内核也有它自己的 **地址空间**。

**User memory refers to a process’s user address space plus the physical memory that the page table allows the process to access.**
**用户内存（User memory）** 指的是某个进程的 **用户地址空间**，再加上页表允许该进程访问的 **物理内存**。

**Virtual memory refers to the ideas and techniques associated with managing page tables and using them to achieve goals such as isolation.**
**虚拟内存（Virtual memory）** 指的是与 **页表管理相关的思想和技术**，其目标包括实现诸如 **进程隔离** 等功能。

### **3.2 内核地址空间（Kernel address space）**

**Xv6 maintains one page table per process, describing each process’s user address space, plus a single page table that describes the kernel’s address space.**
xv6 为每个进程维护一张页表，描述其用户地址空间；同时维护一张单独的页表，描述内核的地址空间。

**The kernel configures the layout of its address space to give itself access to physical memory and various hardware resources at predictable virtual addresses.**
内核会配置自己的地址空间布局，使其在 **可预测的虚拟地址** 处能够访问物理内存和各种硬件资源。

---

**The kernel gets at RAM and memory-mapped device registers using “direct mapping;” that is, mapping the resources at virtual addresses that are equal to the physical address.**
内核通过 **直接映射（direct mapping）** 来访问 RAM 和内存映射的设备寄存器，即把虚拟地址直接映射为和物理地址相同的值。

**For example, the kernel itself is located at `KERNBASE=0x80000000` in both the virtual address space and in physical memory.**
例如，内核自身在虚拟地址空间和物理内存中的地址都是 `KERNBASE=0x80000000`。

**Direct mapping simplifies kernel code that reads or writes physical memory.**
直接映射简化了内核访问物理内存的代码。

---

**There are a couple of kernel virtual addresses that aren’t direct-mapped:**
不过，有两个内核虚拟地址不是直接映射的：

1. **Trampoline page（跳板页）**：

   * 映射在虚拟地址空间的最顶端，用户页表也有同样的映射。
   * 这是一种页表的特殊用法：同一物理页被映射到两个虚拟地址上，一个在空间顶端，一个是直接映射地址。

2. **Kernel stack pages（内核栈页）**：

   * 每个进程都有独立的内核栈，映射在高地址处。
   * 在栈下方留一个未映射的 **保护页（guard page）**，如果栈溢出会触发异常并导致内核 panic，从而避免破坏其他内核内存。

---

**The kernel maps the pages for the trampoline and the kernel text with the permissions PTE\_R and PTE\_X.**
内核将 trampoline 页和内核代码区映射为 **可读（PTE\_R）和可执行（PTE\_X）**。

**The kernel maps the other pages with the permissions PTE\_R and PTE\_W.**
内核的其他页映射为 **可读（PTE\_R）和可写（PTE\_W）**。

**The mappings for the guard pages are invalid.**
保护页的映射则被标记为 **无效（invalid）**。

---

### **3.3 创建地址空间（Code: creating an address space）**

**Most of the xv6 code for manipulating address spaces and page tables resides in vm.c (kernel/vm.c:1).**
大部分与地址空间和页表相关的 xv6 代码都在 `vm.c`（`kernel/vm.c:1`）中。

**The central data structure is pagetable\_t, which is really a pointer to a RISC-V root page-table page; a pagetable\_t may be either the kernel page table, or one of the per-process page tables.**
核心数据结构是 `pagetable_t`，它实际上是一个指向 RISC-V 根页表页的指针。`pagetable_t` 可以是内核的页表，也可以是某个进程的页表。

**The central functions are walk, which finds the PTE for a virtual address, and mappages, which installs PTEs for new mappings.**
核心函数有：

* `walk`：查找某个虚拟地址对应的 PTE；
* `mappages`：为新的映射安装 PTE。

**Functions starting with kvm manipulate the kernel page table; functions starting with uvm manipulate a user page table; other functions are used for both.**
以 `kvm` 开头的函数操作内核页表；以 `uvm` 开头的函数操作用户页表；其他函数则两者通用。

**copyout and copyin copy data to and from user virtual addresses provided as system call arguments; they are in vm.c because they need to explicitly translate those addresses in order to find the corresponding physical memory.**
`copyout` 和 `copyin` 用于在内核和用户虚拟地址之间拷贝数据（这些地址来自系统调用的参数）。它们之所以在 `vm.c` 中，是因为需要显式地翻译这些地址，找到对应的物理内存。

---

**Early in the boot sequence, main calls kvminit (kernel/vm.c:54) to create the kernel’s page table using kvmmake (kernel/vm.c:20).**
在引导序列早期，`main` 调用 `kvminit`（`kernel/vm.c:54`），它通过 `kvmmake`（`kernel/vm.c:20`）创建内核页表。

**This call occurs before xv6 has enabled paging on the RISC-V, so addresses refer directly to physical memory.**
这一步发生在 xv6 启用 RISC-V 分页之前，因此当时的地址直接对应物理内存。

**kvmmake first allocates a page of physical memory to hold the root page-table page. Then it calls kvmmap to install the translations that the kernel needs.**
`kvmmake` 首先分配一个物理页作为根页表，然后调用 `kvmmap` 安装内核所需的映射。

**The translations include the kernel’s instructions and data, physical memory up to PHYSTOP, and memory ranges which are actually devices.**
这些映射包括：内核的指令和数据、直到 `PHYSTOP` 的物理内存、以及一些实际上对应设备的内存区域。

**proc\_mapstacks (kernel/proc.c:33) allocates a kernel stack for each process. It calls kvmmap to map each stack at the virtual address generated by KSTACK, which leaves room for the invalid stack-guard pages.**
`proc_mapstacks`（`kernel/proc.c:33`）为每个进程分配一个内核栈。它调用 `kvmmap` 把栈映射到 `KSTACK` 生成的虚拟地址处，并在栈下方留出一页无效的 **保护页**。

---

**kvmmap (kernel/vm.c:132) calls mappages (kernel/vm.c:144), which installs mappings into a page table for a range of virtual addresses to a corresponding range of physical addresses.**
`kvmmap`（`kernel/vm.c:132`）调用 `mappages`（`kernel/vm.c:144`），把一段虚拟地址范围映射到对应的物理地址范围。

**It does this separately for each virtual address in the range, at page intervals.**
它逐页（以页为单位）完成这一映射。

**For each virtual address to be mapped, mappages calls walk to find the address of the PTE for that address.**
对每个需要映射的虚拟地址，`mappages` 调用 `walk` 来找到对应的 PTE。

**It then initializes the PTE to hold the relevant physical page number, the desired permissions (PTE\_W, PTE\_X, and/or PTE\_R), and PTE\_V to mark the PTE as valid.**
然后初始化该 PTE：填入对应的物理页号、所需权限（`PTE_W`、`PTE_X` 和/或 `PTE_R`），并设置 `PTE_V` 以标记其有效。

---

**walk (kernel/vm.c:86) mimics the RISC-V paging hardware as it looks up the PTE for a virtual address (see Figure 3.2).**
`walk`（`kernel/vm.c:86`）模拟了 RISC-V 分页硬件的工作方式，用于查找虚拟地址对应的 PTE（见图 3.2）。

**walk descends the page table one level at a time, using each level’s 9 bits of virtual address to index into the relevant page directory page.**
`walk` 每次下降一层页表，用虚拟地址中的 9 位来索引对应的页目录页。

**At each level it finds either the PTE of the next level’s page directory page, or the PTE of final page.**
在每一层，它要么找到下一层页目录页的 PTE，要么找到最终页的 PTE。

**If a PTE in a first or second level page directory page isn’t valid, then the required directory page hasn’t yet been allocated; if the alloc argument is set, walk allocates a new page-table page and puts its physical address in the PTE.**
如果某一层（一级或二级）页目录页中的 PTE 无效，说明需要的目录页还没分配；如果 `alloc` 参数被设置，`walk` 就会分配一个新的页表页，并把其物理地址写入该 PTE。

**It returns the address of the PTE in the lowest layer in the tree.**
最后返回树底层 PTE 的地址。

---

**The above code depends on physical memory being direct-mapped into the kernel virtual address space.**
以上代码依赖于 **物理内存直接映射到内核虚拟地址空间**。

**For example, as walk descends levels of the page table, it pulls the (physical) address of the next-level-down page table from a PTE, and then uses that address as a virtual address to fetch the PTE at the next level down.**
例如，当 `walk` 向下遍历页表时，它会从 PTE 中取出下一层页表的 **物理地址**，再把它当作虚拟地址来读取下一层的 PTE。

---

**main calls kvminithart (kernel/vm.c:62) to install the kernel page table.**
`main` 调用 `kvminithart`（`kernel/vm.c:62`）来安装内核页表。

**It writes the physical address of the root page-table page into the register satp.**
它会把根页表的物理地址写入寄存器 `satp`。

**After this the CPU will translate addresses using the kernel page table.**
此后，CPU 将通过内核页表来翻译地址。

**Since the kernel uses a direct mapping, the now virtual address of the next instruction will map to the right physical memory address.**
由于内核采用直接映射，因此接下来的指令虚拟地址将正确映射到物理内存地址。

---

**Each RISC-V CPU caches page table entries in a Translation Look-aside Buffer (TLB),**
每个 RISC-V CPU 会把页表条目缓存到 **TLB（Translation Look-aside Buffer，快表）** 中，

**and when xv6 changes a page table, it must tell the CPU to invalidate corresponding cached TLB entries.**
当 xv6 修改页表时，必须通知 CPU 使相应的 TLB 缓存条目失效。

**If it didn’t, then at some point later the TLB might use an old cached mapping, pointing to a physical page that in the meantime has been allocated to another process, and as a result, a process might be able to scribble on some other process’s memory.**
否则，TLB 可能会继续使用旧的缓存映射，而此时该物理页可能已分配给另一个进程，结果会导致某个进程可以意外修改别的进程的内存。

---

**The RISC-V has an instruction sfence.vma that flushes the current CPU’s TLB.**
RISC-V 提供了一条 `sfence.vma` 指令，用于刷新当前 CPU 的 TLB。

**Xv6 executes sfence.vma in kvminithart after reloading the satp register, and in the trampoline code that switches to a user page table before returning to user space (kernel/trampoline.S:89).**
xv6 会在 `kvminithart` 中重载 `satp` 寄存器后执行 `sfence.vma`，还会在返回用户空间之前的 **trampoline 代码** 中（`kernel/trampoline.S:89`）执行该指令，以切换到用户页表。

---

**It is also necessary to issue sfence.vma before changing satp, in order to wait for completion of all outstanding loads and stores.**
在修改 `satp` 之前，还必须执行一次 `sfence.vma`，以等待所有未完成的加载和存储操作结束。

**This wait ensures that preceding updates to the page table have completed, and ensures that preceding loads and stores use the old page table, not the new one.**
这样可以保证之前对页表的更新已经完成，并且保证之前的加载和存储操作使用的是旧页表，而不是新页表。

---

**To avoid flushing the complete TLB, RISC-V CPUs may support address space identifiers (ASIDs) \[3].**
为了避免每次都清空整个 TLB，RISC-V CPU 可能会支持 **地址空间标识符（ASID）** \[3]。

**The kernel can then flush just the TLB entries for a particular address space.**
这样内核只需刷新某个特定地址空间的 TLB 条目，而不是全部清空。

**Xv6 does not use this feature.**
不过，xv6 并没有使用这一特性。

### **3.4 物理内存分配（Physical memory allocation）**

**The kernel must allocate and free physical memory at run-time for page tables, user memory, kernel stacks, and pipe buffers.**
内核在运行时必须能够分配和释放物理内存，用于 **页表**、**用户内存**、**内核栈** 和 **管道缓冲区**。

---

**Xv6 uses the physical memory between the end of the kernel and PHYSTOP for run-time allocation.**
xv6 使用 **内核末尾到 `PHYSTOP` 之间的物理内存** 作为运行时分配区域。

**It allocates and frees whole 4096-byte pages at a time.**
它每次以 **4096 字节（1 页）** 为单位进行分配和释放。

**It keeps track of which pages are free by threading a linked list through the pages themselves.**
它通过在页面本身中穿插链表的方式来记录哪些页面是空闲的。

**Allocation consists of removing a page from the linked list; freeing consists of adding the freed page to the list.**
分配的过程就是从链表中取出一页；释放的过程就是把释放的页重新加回链表。

---

### **3.5 代码：物理内存分配器（Code: Physical memory allocator）**

**The allocator resides in kalloc.c (kernel/kalloc.c:1).**
内存分配器的实现位于 `kalloc.c`（`kernel/kalloc.c:1`）。

**The allocator’s data structure is a free list of physical memory pages that are available for allocation.**
分配器的数据结构是一个 **空闲链表**，其中保存着所有可分配的物理内存页。

**Each free page’s list element is a struct run (kernel/kalloc.c:17).**
每个空闲页的链表元素是一个 `struct run`（`kernel/kalloc.c:17`）。

**Where does the allocator get the memory to hold that data structure?**
那么，分配器本身用的 `struct run` 数据结构的内存来自哪里呢？

**It store each free page’s run structure in the free page itself, since there’s nothing else stored there.**
答案是：它直接把 `struct run` 存放在空闲页自身，因为空闲页中本来没有存储其他数据。

---

**The free list is protected by a spin lock (kernel/kalloc.c:21-24).**
空闲链表由一个 **自旋锁**（`kernel/kalloc.c:21-24`）保护。

**The list and the lock are wrapped in a struct to make clear that the lock protects the fields in the struct.**
链表和锁被封装在一个结构体中，这样可以明确：该锁负责保护结构体中的字段。

**For now, ignore the lock and the calls to acquire and release; Chapter 6 will examine locking in detail.**
目前可以先忽略锁以及 `acquire` / `release` 调用；第 6 章会详细讨论锁机制。

---

**The function main calls kinit to initialize the allocator (kernel/kalloc.c:27).**
`main` 会调用 `kinit`（`kernel/kalloc.c:27`）来初始化分配器。

**kinit initializes the free list to hold every page between the end of the kernel and PHYSTOP.**
`kinit` 会把 **内核结束地址到 `PHYSTOP` 之间的所有页面** 加入空闲链表。

**Xv6 ought to determine how much physical memory is available by parsing configuration information provided by the hardware. Instead xv6 assumes that the machine has 128 megabytes of RAM.**
严格来说，xv6 应该通过解析硬件提供的配置信息来确定物理内存大小。但实际上，xv6 **假设机器有 128 MB RAM**。

---

**kinit calls freerange to add memory to the free list via per-page calls to kfree.**
`kinit` 调用 `freerange`，后者通过逐页调用 `kfree` 来把内存加入空闲链表。

**A PTE can only refer to a physical address that is aligned on a 4096-byte boundary (is a multiple of 4096), so freerange uses PGROUNDUP to ensure that it frees only aligned physical addresses.**
由于一个 PTE 只能引用 **按 4096 字节（页大小）对齐的物理地址**，`freerange` 会调用 `PGROUNDUP` 来确保只释放对齐的物理地址。

**The allocator starts with no memory; these calls to kfree give it some to manage.**
分配器一开始没有可用内存；正是这些 `kfree` 调用，才给它提供了可管理的空闲内存页。

---

**The allocator sometimes treats addresses as integers in order to perform arithmetic on them (e.g., traversing all pages in freerange),**
分配器有时会把地址当作整数来做运算（例如在 `freerange` 中遍历所有页面）；

**and sometimes uses addresses as pointers to read and write memory (e.g., manipulating the run structure stored in each page);**
有时又会把地址当作指针来读写内存（例如操作存放在页面中的 `run` 结构）；

**this dual use of addresses is the main reason that the allocator code is full of C type casts.**
这种 **整数/指针双重用途** 是分配器代码里充满 C 类型转换的主要原因。

---

**The function kfree (kernel/kalloc.c:47) begins by setting every byte in the memory being freed to the value 1.**
`kfree`（`kernel/kalloc.c:47`）在释放内存时，首先会把该页内的每个字节都设为 `1`。

**This will cause code that uses memory after freeing it (uses “dangling references”) to read garbage instead of the old valid contents; hopefully that will cause such code to break faster.**
这样做的目的是：如果有代码在释放后仍使用该内存（悬空引用），它会读到垃圾数据，而不是之前的有效内容，从而更快暴露问题。

---

**Then kfree prepends the page to the free list: it casts pa to a pointer to struct run, records the old start of the free list in r->next, and sets the free list equal to r.**
接着，`kfree` 会把该页挂回空闲链表表头：

* 把物理地址 `pa` 转换成 `struct run*`；
* 将旧的空闲链表头存到 `r->next`；
* 最后把链表头更新为 `r`。

---

**kalloc removes and returns the first element in the free list.**
`kalloc` 则是从空闲链表中取出第一个元素并返回。

### **3.6 进程地址空间（Process address space）**

**Each process has its own page table, and when xv6 switches between processes, it also changes page tables.**
每个进程都有自己独立的页表，当 xv6 在不同进程之间切换时，它也会切换页表。

**Figure 3.4 shows a process’s address space in more detail than Figure 2.3.**
图 3.4 比图 2.3 更详细地展示了一个进程的地址空间。

**A process’s user memory starts at virtual address zero and can grow up to MAXVA (kernel/riscv.h:375), allowing a process to address in principle 256 Gigabytes of memory.**
进程的用户内存从虚拟地址 **0** 开始，可以增长到 **MAXVA**（`kernel/riscv.h:375`），原则上允许进程寻址多达 **256 GB** 的内存。

---

**A process’s address space consists of pages that contain the text of the program (which xv6 maps with the permissions PTE\_R, PTE\_X, and PTE\_U),**
进程的地址空间包括存放 **程序代码（text 段）** 的页面（xv6 使用 `PTE_R`、`PTE_X` 和 `PTE_U` 权限来映射）；

**pages that contain the pre-initialized data of the program, a page for the stack, and pages for the heap.**
存放 **程序预初始化数据** 的页面、一个 **栈页面**，以及若干 **堆页面**。

**Xv6 maps the data, stack, and heap with the permissions PTE\_R, PTE\_W, and PTE\_U.**
xv6 使用 `PTE_R`、`PTE_W` 和 `PTE_U` 权限来映射 **数据段、栈和堆**。

---

**Using permissions within a user address space is a common technique to harden a user process.**
在用户地址空间内合理使用权限，是强化用户进程的一种常见技术。

**If the text were mapped with PTE\_W, then a process could accidentally modify its own program;**
如果代码段被错误地设置了 `PTE_W`（可写权限），进程就可能意外修改自己的代码；

**for example, a programming error may cause the program to write to a null pointer, modifying instructions at address 0, and then continue running, perhaps creating more havoc.**
例如，一个编程错误可能导致程序向空指针写入数据，从而修改 **地址 0** 的指令，并继续运行，引发更严重的错误。

---

**To detect such errors immediately, xv6 maps the text without PTE\_W;**
为了立即检测到此类错误，xv6 在映射代码段时不会设置 `PTE_W`；

**if a program accidentally attempts to store to address 0, the hardware will refuse to execute the store and raises a page fault (see Section 4.6).**
如果程序意外尝试向地址 0 存储数据，硬件会拒绝执行该操作并触发 **缺页异常**（参见 4.6 节）。

**The kernel then kills the process and prints out an informative message so that the developer can track down the problem.**
此时，内核会终止该进程，并打印提示信息，以便开发者定位问题。

---

**Similarly, by mapping data without PTE\_X, a user program cannot accidentally jump to an address in the program’s data and start executing at that address.**
同样地，xv6 在映射数据段时不会设置 `PTE_X`（可执行权限），这样用户程序就不会因为 bug 而跳转到数据段并开始把它当成指令执行。

---


**The stack is a single page, and is shown with the initial contents as created by exec.**
栈（stack）只有一页，其初始内容由 `exec` 创建。

**Strings containing the command-line arguments, as well as an array of pointers to them, are at the very top of the stack.**
存放命令行参数的字符串，以及指向这些字符串的指针数组，位于栈的最顶端。

**Just under that are values that allow a program to start at main as if the function main(argc, argv) had just been called.**
在其下方，是一些用于启动 `main` 函数的值，就像程序刚刚调用了 `main(argc, argv)` 一样。

---

**To detect a user stack overflowing the allocated stack memory, xv6 places an inaccessible guard page right below the stack by clearing the PTE\_U flag.**
为了检测用户栈是否溢出分配的栈空间，xv6 在栈的下方放置了一个 **不可访问的防护页（guard page）**，其方式是清除 `PTE_U` 标志。

**If the user stack overflows and the process tries to use an address below the stack, the hardware will generate a page-fault exception because the guard page is inaccessible to a program running in user mode.**
如果用户栈发生溢出，进程试图访问栈下方的地址，硬件会因为防护页在用户模式下不可访问而触发 **缺页异常**。

**A real-world operating system might instead automatically allocate more memory for the user stack when it overflows.**
在现实中的操作系统里，更常见的做法是：当用户栈溢出时，操作系统会自动为其分配更多内存。

---

**When a process asks xv6 for more user memory, xv6 grows the process’s heap.**
当一个进程向 xv6 请求更多用户内存时，xv6 会扩展该进程的 **堆（heap）**。

**Xv6 first uses kalloc to allocate physical pages.**
首先，xv6 使用 `kalloc` 分配物理页面。

**It then adds PTEs to the process’s page table that point to the new physical pages.**
然后，它在进程的页表中添加新的 **页表项（PTE）**，指向这些新分配的物理页面。

**Xv6 sets the PTE\_W, PTE\_R, PTE\_U, and PTE\_V flags in these PTEs.**
对于这些新页，xv6 会在 PTE 中设置 `PTE_W`（可写）、`PTE_R`（可读）、`PTE_U`（用户模式可访问）和 `PTE_V`（有效）标志。

**Most processes do not use the entire user address space; xv6 leaves PTE\_V clear in unused PTEs.**
大多数进程不会用完整个用户地址空间；因此，xv6 会在未使用的 PTE 中清除 `PTE_V` 标志。

这里可以看到页表的一些典型用法：

### **3.8 代码：exec**

**exec is a system call that replaces a process’s user address space with data read from a file, called a binary or executable file.**
`exec` 是一个系统调用，用于 **用文件中的数据（即二进制文件或可执行文件）替换进程的用户地址空间**。

**A binary is typically the output of the compiler and linker, and holds machine instructions and program data.**
一个二进制文件通常是编译器和链接器的输出，包含机器指令和程序数据。

**exec (kernel/exec.c:23) opens the named binary path using namei (kernel/exec.c:36), which is explained in Chapter 8.**
`exec`（`kernel/exec.c:23`）通过调用 `namei`（`kernel/exec.c:36`，将在第 8 章解释）打开指定的二进制文件路径。

**Then, it reads the ELF header. Xv6 binaries are formatted in the widely-used ELF format, defined in (kernel/elf.h).**
接着，它会读取 ELF 头部。xv6 的二进制文件采用广泛使用的 **ELF 格式**，该格式定义在 `kernel/elf.h` 中。

**An ELF binary consists of an ELF header, struct elfhdr (kernel/elf.h:6), followed by a sequence of program section headers, struct proghdr (kernel/elf.h:25).**
一个 ELF 二进制文件由 **ELF 头（`struct elfhdr`，`kernel/elf.h:6`）** 和一系列 **程序段头（`struct proghdr`，`kernel/elf.h:25`）** 组成。

**Each proghdr describes a section of the application that must be loaded into memory; xv6 programs have two program section headers: one for instructions and one for data.**
每个 `proghdr` 描述了应用程序中需要加载到内存的一个部分；xv6 程序通常有两个段头：**一个用于代码（指令段），一个用于数据段**。

---

**The first step is a quick check that the file probably contains an ELF binary.**
第一步是快速检查该文件是否是一个 ELF 二进制文件。

**An ELF binary starts with the four-byte “magic number” 0x7F, ‘E’, ‘L’, ‘F’, or ELF\_MAGIC (kernel/elf.h:3).**
一个 ELF 文件的开头必须包含四字节的 **魔数**：`0x7F`、`E`、`L`、`F`（即 `ELF_MAGIC`，定义在 `kernel/elf.h:3`）。

**If the ELF header has the right magic number, exec assumes that the binary is well-formed.**
如果 ELF 头包含正确的魔数，`exec` 就假定该二进制文件是格式正确的。

**exec places an inaccessible page just below the stack page, so that programs that try to use more than one page will fault.**
`exec` 在栈页下方放置了一个 **不可访问的页面**，这样如果程序尝试使用超过一页的栈，就会触发 **异常（fault）**。

**This inaccessible page also allows exec to deal with arguments that are too large;**
这个不可访问页还帮助 `exec` 处理 **过大的参数列表**；

**in that situation, the copyout (kernel/vm.c:359) function that exec uses to copy arguments to the stack will notice that the destination page is not accessible, and will return -1.**
在这种情况下，`exec` 使用的 `copyout`（`kernel/vm.c:359`）函数会发现目标页不可访问，并返回 `-1`。

**During the preparation of the new memory image, if exec detects an error like an invalid program segment, it jumps to the label bad, frees the new image, and returns -1.**
在构建新的内存镜像过程中，如果 `exec` 检测到错误（例如无效的程序段），它会跳转到标签 `bad`，释放新镜像，并返回 `-1`。

**exec must wait to free the old image until it is sure that the system call will succeed: if the old image is gone, the system call cannot return -1 to it.**
`exec` 必须等到确认系统调用能够成功后，才能释放旧的内存镜像；否则，如果旧镜像已经被释放，就无法返回 `-1` 给它。

**The only error cases in exec happen during the creation of the image. Once the image is complete, exec can commit to the new page table (kernel/exec.c:125) and free the old one (kernel/exec.c:129).**
`exec` 的错误情况只会发生在构建新镜像的过程中。一旦新镜像创建完成，`exec` 就会提交新的页表（`kernel/exec.c:125`），并释放旧的页表（`kernel/exec.c:129`）。

**exec loads bytes from the ELF file into memory at addresses specified by the ELF file.**
`exec` 会按照 ELF 文件中指定的地址，将字节加载到内存中。

**Users or processes can place whatever addresses they want into an ELF file.**
用户或进程可以在 ELF 文件中写入任意地址。

**Thus exec is risky, because the addresses in the ELF file may refer to the kernel, accidentally or on purpose.**
因此，`exec` 是存在风险的，因为 ELF 文件中的地址可能会 **无意或恶意地指向内核**。

**The consequences for an unwary kernel could range from a crash to a malicious subversion of the kernel’s isolation mechanisms (i.e., a security exploit).**
对一个没有防护的内核来说，后果可能从 **崩溃** 到 **恶意绕过内核的隔离机制**（即安全漏洞）。

**Xv6 performs a number of checks to avoid these risks. For example if(ph.vaddr + ph.memsz < ph.vaddr) checks for whether the sum overflows a 64-bit integer.**
为了避免这些风险，xv6 做了一些检查。例如：`if(ph.vaddr + ph.memsz < ph.vaddr)` 检查求和是否会溢出 64 位整数。

**The danger is that a user could construct an ELF binary with a ph.vaddr that points to a user-chosen address, and ph.memsz large enough that the sum overflows to 0x1000, which will look like a valid value.**
风险在于：用户可能构造一个 ELF 文件，其中 `ph.vaddr` 指向一个自选地址，而 `ph.memsz` 足够大，使得相加后溢出为 `0x1000`，看起来像是一个有效值。

**In an older version of xv6 in which the user address space also contained the kernel (but not readable/writable in user mode), the user could choose an address that corresponded to kernel memory and would thus copy data from the ELF binary into the kernel.**
在旧版 xv6 中，用户地址空间包含了内核（虽然用户模式下不可读写），用户可能选择一个对应内核内存的地址，从而把 ELF 文件的数据复制到内核中。

**In the RISC-V version of xv6 this cannot happen, because the kernel has its own separate page table; loadseg loads into the process’s page table, not in the kernel’s page table.**
但在 RISC-V 版本的 xv6 中，这种情况不会发生，因为 **内核有独立的页表**；`loadseg` 加载的是进程的页表，而不是内核的页表。
