
### Traps and system calls
---

**There are three kinds of event which cause the CPU to set aside ordinary execution of instructions and force a transfer of control to special code that handles the event.**
有三类事件会使 CPU 中断正常的指令执行，并强制将控制权转移到专门的处理代码。

**One situation is a system call, when a user program executes the ecall instruction to ask the kernel to do something for it.**
第一类情况是 **系统调用 (system call)**，当用户程序执行 `ecall` 指令，请求内核代为完成某项操作时。

**Another situation is an exception: an instruction (user or kernel) does something illegal, such as divide by zero or use an invalid virtual address.**
第二类情况是 **异常 (exception)**：当某条指令（无论来自用户态还是内核态）执行了非法操作，例如除以零，或者使用了无效的虚拟地址。

**The third situation is a device interrupt, when a device signals that it needs attention, for example when the disk hardware finishes a read or write request.**
第三类情况是 **设备中断 (device interrupt)**：当某个设备发出信号请求处理时，例如磁盘硬件完成一次读写操作。

---

**This book uses trap as a generic term for these situations.**
本书将这三类情况统称为 **trap（陷阱/陷入）**。

**Typically whatever code was executing at the time of the trap will later need to resume, and shouldn’t need to be aware that anything special happened.**
通常来说，trap 发生时正在运行的代码在稍后需要继续执行，并且不应该察觉到发生了什么特殊事件。

**That is, we often want traps to be transparent; this is particularly important for device interrupts, which the interrupted code typically doesn’t expect.**
也就是说，我们希望 trap 对程序是“透明的”；这对设备中断尤其重要，因为被中断的代码通常并没有预料到中断的发生。

**The usual sequence is that a trap forces a transfer of control into the kernel; the kernel saves registers and other state so that execution can be resumed; the kernel executes appropriate handler code (e.g., a system call implementation or device driver); the kernel restores the saved state and returns from the trap; and the original code resumes where it left off.**
常见的处理流程是：trap 将控制权转交给内核 → 内核保存寄存器和其他状态以便恢复 → 内核执行相应的处理程序（例如系统调用的实现或设备驱动程序） → 内核恢复保存的状态并从 trap 返回 → 原始代码从中断点继续执行。

---

**Xv6 handles all traps in the kernel; traps are not delivered to user code.**
在 xv6 中，所有 trap 都由内核处理；它们不会直接传递给用户代码。

**Handling traps in the kernel is natural for system calls.**
系统调用由内核处理是理所当然的。

**It makes sense for interrupts since isolation demands that only the kernel be allowed to use devices, and because the kernel is a convenient mechanism with which to share devices among multiple processes.**
中断由内核处理也合理，因为 **隔离性要求只有内核才能直接操作设备**，而且内核提供了一个便捷的机制来在多个进程之间共享设备。

**It also makes sense for exceptions since xv6 responds to all exceptions from user space by killing the offending program.**
异常由内核处理同样合理，因为 xv6 对用户空间发生的所有异常的处理方式都是 **终止触发异常的程序**。

---

**Xv6 trap handling proceeds in four stages: hardware actions taken by the RISC-V CPU, some assembly instructions that prepare the way for kernel C code, a C function that decides what to do with the trap, and the system call or device-driver service routine.**
xv6 的 trap 处理分为四个阶段：

1. **硬件操作** —— 由 RISC-V CPU 自动执行；
2. **汇编准备** —— 一些汇编指令，为进入内核 C 代码做准备；
3. **C 语言分发** —— 内核中的 C 函数决定如何处理该 trap；
4. **服务例程执行** —— 调用系统调用实现或设备驱动服务例程。

**While commonality among the three trap types suggests that a kernel could handle all traps with a single code path, it turns out to be convenient to have separate code for two distinct cases: traps from user space, and traps from kernel space.**
虽然三类 trap 有一定共性，理论上内核可以使用同一条代码路径处理所有 trap，但实践中更方便的做法是区分两种情况：**来自用户空间的 trap** 和 **来自内核空间的 trap**。

**Kernel code (assembler or C) that processes a trap is often called a handler; the first handler instructions are usually written in assembler (rather than C) and are sometimes called a vector.**
处理 trap 的内核代码（无论是汇编还是 C）通常称为 **handler（处理程序）**；其中最初的几条处理指令通常用汇编编写（而不是 C），有时称为 **vector（向量/入口向量）**。

**4.1 RISC-V trap machinery** 

**Each RISC-V CPU has a set of control registers that the kernel writes to tell the CPU how to handle traps, and that the kernel can read to find out about a trap that has occurred.**
每个 RISC-V CPU 都有一组控制寄存器，内核通过写入这些寄存器来告诉 CPU 如何处理 trap，并且内核可以通过读取它们来了解已发生的 trap。

**The RISC-V documents contain the full story \[3]. riscv.h (kernel/riscv.h:1) contains definitions that xv6 uses.**
RISC-V 官方文档中有完整的说明 \[3]。xv6 在 `riscv.h`（文件路径 `kernel/riscv.h:1`）中包含了相关的定义。

**Here’s an outline of the most important registers:**
下面是几个最重要的寄存器概要：

* **stvec**: The kernel writes the address of its trap handler here; the RISC-V jumps to the address in stvec to handle a trap.
  **stvec**：内核将其 trap 处理程序的地址写入此寄存器；RISC-V 在发生 trap 时会跳转到 `stvec` 中的地址执行处理。

* **sepc**: When a trap occurs, RISC-V saves the program counter here (since the pc is then overwritten with the value in stvec). The sret (return from trap) instruction copies sepc to the pc. The kernel can write sepc to control where sret goes.
  **sepc**：当 trap 发生时，RISC-V 将当前的程序计数器 (pc) 保存到这里（因为 pc 会被 `stvec` 中的值覆盖）。`sret`（从 trap 返回）指令会把 `sepc` 的值复制到 pc。内核可以写入 `sepc` 来控制 `sret` 返回的位置。

* **scause**: RISC-V puts a number here that describes the reason for the trap.
  **scause**：RISC-V 在此寄存器中写入一个数值，用于描述 trap 的原因。

* **sscratch**: The trap handler code uses sscratch to help it avoid overwriting user registers before saving them.
  **sscratch**：trap 处理程序会使用 `sscratch`，以避免在保存用户寄存器之前覆盖它们。

* **sstatus**: The SIE bit in sstatus controls whether device interrupts are enabled. If the kernel clears SIE, the RISC-V will defer device interrupts until the kernel sets SIE. The SPP bit indicates whether a trap came from user mode or supervisor mode, and controls to what mode sret returns.
  **sstatus**：其中的 **SIE 位** 用来控制是否启用设备中断。如果内核清除了 SIE 位，RISC-V 将延迟处理设备中断，直到内核重新设置 SIE 位。**SPP 位** 用来指示 trap 来源于用户态还是管理态，并决定 `sret` 返回到哪种模式。

---

**The above registers relate to traps handled in supervisor mode, and they cannot be read or written in user mode.**
上述寄存器与在 **管理态 (supervisor mode)** 下处理的 trap 有关，在用户态下不能读写。

**Each CPU on a multi-core chip has its own set of these registers, and more than one CPU may be handling a trap at any given time.**
多核芯片上的每个 CPU 都有自己的一组寄存器，并且在某一时刻可能有多个 CPU 同时在处理 trap。

---

**When it needs to force a trap, the RISC-V hardware does the following for all trap types:**
当需要强制进入 trap 时，RISC-V 硬件对所有 trap 类型都会执行以下步骤：

1. **If the trap is a device interrupt, and the sstatus SIE bit is clear, don’t do any of the following.**
   如果 trap 是设备中断，并且 `sstatus` 中的 SIE 位被清除，则不执行以下操作。

2. **Disable interrupts by clearing the SIE bit in sstatus.**
   通过清除 `sstatus` 中的 SIE 位来关闭中断。

3. **Copy the pc to sepc.**
   将当前 pc 保存到 `sepc`。

4. **Save the current mode (user or supervisor) in the SPP bit in sstatus.**
   将当前的运行模式（用户态或管理态）保存到 `sstatus` 的 SPP 位中。

5. **Set scause to reflect the trap’s cause.**
   设置 `scause`，反映 trap 的原因。

6. **Set the mode to supervisor.**
   将模式切换到管理态 (supervisor mode)。

7. **Copy stvec to the pc.**
   将 `stvec` 的值复制到 pc。

8. **Start executing at the new pc.**
   从新的 pc 开始执行。

---

**Note that the CPU doesn’t switch to the kernel page table, doesn’t switch to a stack in the kernel, and doesn’t save any registers other than the pc. Kernel software must perform these tasks.**
需要注意的是，CPU 在 trap 发生时 **不会自动切换到内核页表，也不会切换到内核栈，更不会保存除 pc 之外的其他寄存器**。这些工作必须由内核软件来完成。

**One reason that the CPU does minimal work during a trap is to provide flexibility to software; for example, some operating systems omit a page table switch in some situations to increase trap performance.**
CPU 在 trap 过程中只做最少工作，是为了给软件留出更大的灵活性。例如，一些操作系统在某些情况下会省略页表切换，以提升 trap 的性能。

---

**It’s worth thinking about whether any of the steps listed above could be omitted, perhaps in search of faster traps.**
值得思考的是，上述步骤中是否有一些可以被省略，以追求更快的 trap 处理。

**Though there are situations in which a simpler sequence can work, many of the steps would be dangerous to omit in general.**
虽然在某些特定情况下，简化的流程可能可行，但通常情况下省略这些步骤会非常危险。

**For example, suppose that the CPU didn’t switch program counters. Then a trap from user space could switch to supervisor mode while still running user instructions.**
举例来说，如果 CPU 不切换程序计数器 (pc)，那么来自用户态的 trap 就可能在执行用户指令的同时切换到管理态。

**Those user instructions could break user/kernel isolation, for example by modifying the satp register to point to a page table that allowed accessing all of physical memory.**
这些用户指令可能会破坏用户态/内核态的隔离性，例如修改 `satp` 寄存器，使其指向一个允许访问整个物理内存的页表。

**It is thus important that the CPU switch to a kernel-specified instruction address, namely stvec.**
因此，CPU 切换到一个由内核指定的指令地址（即 `stvec`）是至关重要的。

**4.2 Traps from user space** 

**Xv6 handles traps differently depending on whether the trap occurs while executing in the kernel or in user code.**
xv6 对 trap 的处理方式会因 trap 发生在内核执行期间还是用户代码执行期间而不同。

**Here is the story for traps from user code; Section 4.5 describes traps from kernel code.**
这里讲述的是 **用户态 trap** 的处理流程；第 4.5 节将描述 **内核态 trap** 的处理。

---

**A trap may occur while executing in user space if the user program makes a system call (ecall instruction), or does something illegal, or if a device interrupts.**
在用户态执行时可能发生 trap，例如用户程序执行系统调用（`ecall` 指令）、执行了非法操作，或者设备产生中断。

**The high-level path of a trap from user space is uservec (kernel/trampoline.S:22), then usertrap (kernel/trap.c:37); and when returning, usertrapret (kernel/trap.c:90) and then userret (kernel/trampoline.S:101).**
用户态 trap 的高层执行路径是：

* 进入时：`uservec`（`kernel/trampoline.S:22`） → `usertrap`（`kernel/trap.c:37`）
* 返回时：`usertrapret`（`kernel/trap.c:90`） → `userret`（`kernel/trampoline.S:101`）。

---

**A major constraint on the design of xv6’s trap handling is the fact that the RISC-V hardware does not switch page tables when it forces a trap.**
xv6 trap 处理设计中的一个主要约束是：RISC-V 硬件在强制进入 trap 时 **不会切换页表**。

**This means that the trap handler address in stvec must have a valid mapping in the user page table, since that’s the page table in force when the trap handling code starts executing.**
这意味着 `stvec` 中的 trap 处理程序地址必须在 **用户页表** 中有一个有效映射，因为 trap 处理代码开始执行时，仍然使用的是用户页表。

**Furthermore, xv6’s trap handling code needs to switch to the kernel page table; in order to be able to continue executing after that switch, the kernel page table must also have a mapping for the handler pointed to by stvec.**
此外，xv6 的 trap 处理代码需要切换到内核页表；为了在切换之后能继续执行，**内核页表中也必须包含指向 `stvec` 的处理程序的映射**。

---

**Xv6 satisfies these requirements using a trampoline page.**
xv6 使用 **trampoline 页面** 来满足这些要求。

**The trampoline page contains uservec, the xv6 trap handling code that stvec points to.**
trampoline 页面包含 `uservec`，即 `stvec` 所指向的 xv6 trap 处理代码。

**The trampoline page is mapped in every process’s page table at address TRAMPOLINE, which is at the top of the virtual address space so that it will be above memory that programs use for themselves.**
trampoline 页面在每个进程的页表中都被映射到地址 **TRAMPOLINE**，它位于虚拟地址空间的最顶端，高于程序本身使用的内存。

**The trampoline page is also mapped at address TRAMPOLINE in the kernel page table. See Figure 2.3 and Figure 3.3.**
trampoline 页面在内核页表中也映射在相同的 **TRAMPOLINE 地址**。参见图 2.3 和图 3.3。

**Because the trampoline page is mapped in the user page table, traps can start executing there in supervisor mode.**
由于 trampoline 页面在用户页表中有映射，trap 可以在 **管理态 (supervisor mode)** 从该页面开始执行。

**Because the trampoline page is mapped at the same address in the kernel address space, the trap handler can continue to execute after it switches to the kernel page table.**
由于 trampoline 页面在内核地址空间也映射在相同地址，trap 处理程序在切换到内核页表后仍能继续执行。

---

**The code for the uservec trap handler is in trampoline.S (kernel/trampoline.S:22).**
`uservec` trap 处理程序的代码位于 `trampoline.S`（`kernel/trampoline.S:22`）。

**When uservec starts, all 32 registers contain values owned by the interrupted user code.**
当 `uservec` 开始执行时，所有 32 个寄存器都保存着被中断的用户代码的值。

**These 32 values need to be saved somewhere in memory, so that later on the kernel can restore them before returning to user space.**
这些 32 个寄存器的值需要被保存到内存中，以便稍后在返回用户态之前，内核可以恢复它们。

**Storing to memory requires use of a register to hold the address, but at this point there are no general-purpose registers available!**
但存入内存需要一个寄存器来存放地址，而此时并没有可用的通用寄存器！

**Luckily RISC-V provides a helping hand in the form of the sscratch register.**
幸运的是，RISC-V 提供了一个帮助工具 —— **sscratch 寄存器**。

**The csrw instruction at the start of uservec saves a0 in sscratch. Now uservec has one register (a0) to play with.**
在 `uservec` 的开头，`csrw` 指令会将 `a0` 保存到 `sscratch` 中。这样 `uservec` 就可以使用一个寄存器（`a0`）来进行后续操作了。

---

好的，我来逐句为您翻译这部分 **uservec → usertrap → usertrapret → userret** 的内容，并保持术语准确：

---

**uservec’s next task is to save the 32 user registers.**
`uservec` 的下一个任务是保存 32 个用户寄存器。

**The kernel allocates, for each process, a page of memory for a trapframe structure that (among other things) has space to save the 32 user registers (kernel/proc.h:43).**
内核为每个进程分配一页内存，用于存放一个 **trapframe 结构**（定义见 `kernel/proc.h:43`），其中包含保存 32 个用户寄存器的空间（以及其他信息）。

**Because satp still refers to the user page table, uservec needs the trapframe to be mapped in the user address space.**
由于 `satp` 此时仍然指向用户页表，`uservec` 需要 `trapframe` 在用户地址空间中有映射。

**Xv6 maps each process’s trapframe at virtual address TRAPFRAME in that process’s user page table; TRAPFRAME is just below TRAMPOLINE.**
xv6 将每个进程的 `trapframe` 映射在该进程用户页表中的虚拟地址 **TRAPFRAME**，它紧挨在 **TRAMPOLINE** 之下。

**The process’s p->trapframe also points to the trapframe, though at its physical address so the kernel can use it through the kernel page table.**
进程的 `p->trapframe` 也指向 `trapframe`，不过是通过物理地址来访问，以便内核可以通过内核页表使用它。

---

**Thus uservec loads address TRAPFRAME into a0 and saves all the user registers there, including the user’s a0, read back from sscratch.**
因此，`uservec` 将地址 **TRAPFRAME** 加载到 `a0`，并将所有用户寄存器保存到那里，包括用户的 `a0`（该值需从 `sscratch` 中读回）。

---

**The trapframe contains the address of the current process’s kernel stack, the current CPU’s hartid, the address of the usertrap function, and the address of the kernel page table.**
`trapframe` 中包含当前进程的 **内核栈地址**、当前 CPU 的 **hartid**、`usertrap` 函数的地址，以及 **内核页表的地址**。

**uservec retrieves these values, switches satp to the kernel page table, and jumps to usertrap.**
`uservec` 取出这些值，将 `satp` 切换到内核页表，并跳转到 `usertrap`。

---

**The job of usertrap is to determine the cause of the trap, process it, and return (kernel/trap.c:37).**
`usertrap` 的工作是确定 trap 的原因，进行处理，并最终返回（代码见 `kernel/trap.c:37`）。

**It first changes stvec so that a trap while in the kernel will be handled by kernelvec rather than uservec.**
它首先修改 `stvec`，确保内核态发生的 trap 会由 `kernelvec` 处理，而不是 `uservec`。

**It saves the sepc register (the saved user program counter), because usertrap might call yield to switch to another process’s kernel thread, and that process might return to user space, in the process of which it will modify sepc.**
它保存 `sepc`（即保存的用户程序计数器），因为 `usertrap` 可能会调用 `yield` 切换到另一个进程的内核线程，而那个进程在返回用户态的过程中可能会修改 `sepc`。

**If the trap is a system call, usertrap calls syscall to handle it; if a device interrupt, devintr; otherwise it’s an exception, and the kernel kills the faulting process.**
如果 trap 是系统调用，`usertrap` 调用 `syscall` 处理；如果是设备中断，则调用 `devintr`；否则就是异常，内核会杀死出错的进程。

**The system call path adds four to the saved user program counter because RISC-V, in the case of a system call, leaves the program pointer pointing to the ecall instruction but user code needs to resume executing at the subsequent instruction.**
系统调用路径中，保存的用户程序计数器会加 4，这是因为在系统调用的情况下，RISC-V 会让程序指针仍然指向 `ecall` 指令，但用户代码需要从 `ecall` 的下一条指令恢复执行。

---

**On the way out, usertrap checks if the process has been killed or should yield the CPU (if this trap is a timer interrupt).**
在返回之前，`usertrap` 会检查进程是否已被杀死，或者是否需要让出 CPU（如果 trap 是定时器中断）。

---

**The first step in returning to user space is the call to usertrapret (kernel/trap.c:90).**
返回用户态的第一步是调用 `usertrapret`（代码在 `kernel/trap.c:90`）。

**This function sets up the RISC-V control registers to prepare for a future trap from user space: setting stvec to uservec and preparing the trapframe fields that uservec relies on.**
该函数会设置 RISC-V 的控制寄存器，为将来用户态 trap 做好准备：将 `stvec` 设为 `uservec`，并初始化 `uservec` 所依赖的 `trapframe` 字段。

**usertrapret sets sepc to the previously saved user program counter.**
`usertrapret` 将 `sepc` 设置为先前保存的用户程序计数器。

**At the end, usertrapret calls userret on the trampoline page that is mapped in both user and kernel page tables; the reason is that assembly code in userret will switch page tables.**
最后，`usertrapret` 调用位于 **trampoline 页面**上的 `userret`。该页面在用户和内核页表中都被映射，其原因是 `userret` 中的汇编代码会执行 **页表切换**。

---

**usertrapret’s call to userret passes a pointer to the process’s user page table in a0 (kernel/trampoline.S:101).**
`usertrapret` 调用 `userret` 时，会将进程的用户页表指针传入 `a0`（见 `kernel/trampoline.S:101`）。

**userret switches satp to the process’s user page table.**
`userret` 将 `satp` 切换到该进程的用户页表。

**Recall that the user page table maps both the trampoline page and TRAPFRAME, but nothing else from the kernel.**
回忆一下，用户页表中仅映射了 **trampoline 页面** 和 **TRAPFRAME**，而没有其他内核内容。

**The trampoline page mapping at the same virtual address in user and kernel page tables allows userret to keep executing after changing satp.**
由于 trampoline 页面在用户和内核页表中映射在相同的虚拟地址，`userret` 在切换 `satp` 后仍然可以继续执行。

**From this point on, the only data userret can use is the register contents and the content of the trapframe.**
从这一刻起，`userret` 唯一能使用的数据就是寄存器内容和 `trapframe` 的内容。

**userret loads the TRAPFRAME address into a0, restores saved user registers from the trapframe via a0, restores the saved user a0, and executes sret to return to user space.**
`userret` 将 **TRAPFRAME** 地址加载到 `a0`，通过 `a0` 从 `trapframe` 恢复保存的用户寄存器，恢复保存的用户 `a0`，最后执行 `sret` 返回用户态。

**4.3 Code: Calling system calls** 


**Chapter 2 ended with initcode.S invoking the exec system call (user/initcode.S:11).**
第二章的结尾是 `initcode.S` 调用了 `exec` 系统调用（见 `user/initcode.S:11`）。

**Let’s look at how the user call makes its way to the exec system call’s implementation in the kernel.**
我们来看看用户调用是如何进入内核，并最终执行 `exec` 系统调用的实现。

---

**initcode.S places the arguments for exec in registers a0 and a1, and puts the system call number in a7.**
`initcode.S` 将 `exec` 的参数放入寄存器 `a0` 和 `a1`，并将系统调用号放入 `a7`。

**System call numbers match the entries in the syscalls array, a table of function pointers (kernel/syscall.c:107).**
系统调用号对应于 `syscalls` 数组中的条目，该数组是一个函数指针表（见 `kernel/syscall.c:107`）。

**The ecall instruction traps into the kernel and causes uservec, usertrap, and then syscall to execute, as we saw above.**
`ecall` 指令触发 trap 进入内核，然后依次执行 `uservec`、`usertrap`，最后执行 `syscall`，就像我们前面所看到的那样。

---

**syscall (kernel/syscall.c:132) retrieves the system call number from the saved a7 in the trapframe and uses it to index into syscalls.**
`syscall`（见 `kernel/syscall.c:132`）从 `trapframe` 中保存的 `a7` 里取出系统调用号，并用它作为索引查找 `syscalls` 数组。

**For the first system call, a7 contains SYS\_exec (kernel/syscall.h:8), resulting in a call to the system call implementation function sys\_exec.**
对于第一个系统调用，`a7` 中包含的是 `SYS_exec`（见 `kernel/syscall.h:8`），于是调用了系统调用实现函数 `sys_exec`。

---

**When sys\_exec returns, syscall records its return value in p->trapframe->a0.**
当 `sys_exec` 返回时，`syscall` 会将返回值记录到 `p->trapframe->a0` 中。

**This will cause the original user-space call to exec() to return that value, since the C calling convention on RISC-V places return values in a0.**
这会使最初用户空间调用的 `exec()` 返回该值，因为 RISC-V 的 C 调用约定规定返回值存放在 `a0` 中。

---

**System calls conventionally return negative numbers to indicate errors, and zero or positive numbers for success.**
系统调用通常约定：返回负数表示错误，返回零或正数表示成功。

**If the system call number is invalid, syscall prints an error and returns −1.**
如果系统调用号无效，`syscall` 会打印错误信息并返回 `-1`。

**4.4 Code: System call arguments** 这一节，保持技术术语准确、表达自然：

---

**System call implementations in the kernel need to find the arguments passed by user code.**
内核中的系统调用实现需要获取用户代码传递的参数。

**Because user code calls system call wrapper functions, the arguments are initially where the RISC-V C calling convention places them: in registers.**
由于用户代码调用的是系统调用封装函数，参数最初按照 RISC-V 的 C 调用约定被放置在寄存器中。

**The kernel trap code saves user registers to the current process’s trap frame, where kernel code can find them.**
内核的 trap 代码会把用户寄存器保存到当前进程的 **trapframe** 中，内核代码就可以在那里找到它们。

**The kernel functions argint, argaddr, and argfd retrieve the n’th system call argument from the trap frame as an integer, pointer, or a file descriptor.**
内核函数 `argint`、`argaddr` 和 `argfd` 可以分别以整数、指针或文件描述符的形式，从 `trapframe` 中取出第 `n` 个系统调用参数。

**They all call argraw to retrieve the appropriate saved user register (kernel/syscall.c:34).**
它们都会调用 `argraw` 来获取相应的已保存用户寄存器（见 `kernel/syscall.c:34`）。

---

**Some system calls pass pointers as arguments, and the kernel must use those pointers to read or write user memory.**
有些系统调用会传递指针作为参数，内核必须通过这些指针去读写用户内存。

**The exec system call, for example, passes the kernel an array of pointers referring to string arguments in user space.**
例如，`exec` 系统调用会传递一个指针数组给内核，该数组指向用户空间中的字符串参数。

**These pointers pose two challenges.**
这些指针带来两个挑战：

**First, the user program may be buggy or malicious, and may pass the kernel an invalid pointer or a pointer intended to trick the kernel into accessing kernel memory instead of user memory.**
首先，用户程序可能存在 bug 或是恶意的，它可能传递一个无效指针，或者故意传递一个试图让内核访问 **内核内存而不是用户内存** 的指针。

**Second, the xv6 kernel page table mappings are not the same as the user page table mappings, so the kernel cannot use ordinary instructions to load or store from user-supplied addresses.**
其次，xv6 的内核页表映射与用户页表映射不同，因此内核不能直接使用普通指令去访问用户提供的地址。

---

**The kernel implements functions that safely transfer data to and from user-supplied addresses.**
内核实现了一些函数，用于在用户提供的地址与内核之间安全地传输数据。

**fetchstr is an example (kernel/syscall.c:25).**
`fetchstr` 就是其中的一个例子（见 `kernel/syscall.c:25`）。

**File system calls such as exec use fetchstr to retrieve string file-name arguments from user space.**
文件系统调用（例如 `exec`）会使用 `fetchstr` 从用户空间获取字符串形式的文件名参数。

**fetchstr calls copyinstr to do the hard work.**
`fetchstr` 调用 `copyinstr` 来完成主要工作。

---

**copyinstr (kernel/vm.c:415) copies up to max bytes to dst from virtual address srcva in the user page table pagetable.**
`copyinstr`（见 `kernel/vm.c:415`）会从用户页表 `pagetable` 中的虚拟地址 `srcva` 复制最多 `max` 个字节到 `dst`。

**Since pagetable is not the current page table, copyinstr uses walkaddr (which calls walk) to look up srcva in pagetable, yielding physical address pa0.**
由于 `pagetable` 不是当前正在使用的页表，`copyinstr` 会调用 `walkaddr`（其内部调用 `walk`）在 `pagetable` 中查找 `srcva`，得到物理地址 `pa0`。

**The kernel’s page table maps all of physical RAM at virtual addresses that are equal to the RAM’s physical address.**
内核的页表将所有物理内存都映射到与其物理地址相同的虚拟地址上。

**This allows copyinstr to directly copy string bytes from pa0 to dst.**
这样一来，`copyinstr` 就可以直接把字符串字节从 `pa0` 复制到 `dst`。

---

**walkaddr (kernel/vm.c:109) checks that the user-supplied virtual address is part of the process’s user address space, so programs cannot trick the kernel into reading other memory.**
`walkaddr`（见 `kernel/vm.c:109`）会检查用户提供的虚拟地址是否属于该进程的用户地址空间，从而防止程序欺骗内核去读取其他内存。

**A similar function, copyout, copies data from the kernel to a user-supplied address.**
一个类似的函数 `copyout` 则用于将数据从内核复制到用户提供的地址。

**4.5 Traps from kernel space** 

**Xv6 handles traps from kernel code in a different way than traps from user code.**
xv6 对 **内核代码产生的 trap** 的处理方式与 **用户代码产生的 trap** 不同。

**When entering the kernel, usertrap points stvec to the assembly code at kernelvec (kernel/kernelvec.S:12).**
当进入内核时，`usertrap` 会把 `stvec` 指向 `kernelvec`（汇编代码，见 `kernel/kernelvec.S:12`）。

**Since kernelvec only executes if xv6 was already in the kernel, kernelvec can rely on satp being set to the kernel page table, and on the stack pointer referring to a valid kernel stack.**
由于 `kernelvec` 只会在 xv6 已经处于内核态时执行，它可以依赖于以下假设：`satp` 已经设置为内核页表，栈指针也指向了一个有效的内核栈。

**kernelvec pushes all 32 registers onto the stack, from which it will later restore them so that the interrupted kernel code can resume without disturbance.**
`kernelvec` 会将所有 32 个寄存器压入栈中，之后会从栈中恢复它们，以便被中断的内核代码可以不受干扰地继续执行。

---

**kernelvec saves the registers on the stack of the interrupted kernel thread, which makes sense because the register values belong to that thread.**
`kernelvec` 将寄存器保存到 **被中断的内核线程的栈** 上，这是合理的，因为寄存器的值属于该线程。

**This is particularly important if the trap causes a switch to a different thread – in that case the trap will actually return from the stack of the new thread, leaving the interrupted thread’s saved registers safely on its stack.**
这在 trap 导致切换到另一个线程时尤为重要 —— 在这种情况下，trap 实际上会从新线程的栈中返回，而被中断线程的寄存器仍然安全地保存在它自己的栈上。

---

**kernelvec jumps to kerneltrap (kernel/trap.c:135) after saving registers.**
寄存器保存完毕后，`kernelvec` 跳转到 `kerneltrap`（见 `kernel/trap.c:135`）。

**kerneltrap is prepared for two types of traps: device interrupts and exceptions.**
`kerneltrap` 用来处理两类 trap：**设备中断** 和 **异常**。

**It calls devintr (kernel/trap.c:185) to check for and handle the former.**
它调用 `devintr`（见 `kernel/trap.c:185`）来检查并处理设备中断。

**If the trap isn’t a device interrupt, it must be an exception, and that is always a fatal error if it occurs in the xv6 kernel; the kernel calls panic and stops executing.**
如果 trap 不是设备中断，那么它必然是异常，而在 xv6 内核中出现异常总是致命错误；此时内核会调用 `panic` 并停止执行。

---

**If kerneltrap was called due to a timer interrupt, and a process’s kernel thread is running (as opposed to a scheduler thread), kerneltrap calls yield to give other threads a chance to run.**
如果 `kerneltrap` 是由于 **定时器中断** 被调用，并且此时正在运行的是某个进程的内核线程（而不是调度器线程），那么 `kerneltrap` 会调用 `yield`，让出 CPU，给其他线程运行的机会。

**At some point one of those threads will yield, and let our thread and its kerneltrap resume again. Chapter 7 explains what happens in yield.**
最终某个线程会调用 `yield`，让出 CPU，从而使我们的线程和它的 `kerneltrap` 得以恢复执行。第 7 章会解释 `yield` 的细节。

---

**When kerneltrap’s work is done, it needs to return to whatever code was interrupted by the trap.**
当 `kerneltrap` 完成工作后，需要返回到 trap 中断的那段代码继续执行。

**Because a yield may have disturbed sepc and the previous mode in sstatus, kerneltrap saves them when it starts.**
由于 `yield` 可能会改变 `sepc` 和 `sstatus` 中保存的先前模式，`kerneltrap` 在一开始会先保存它们。

**It now restores those control registers and returns to kernelvec (kernel/kernelvec.S:38).**
然后，它恢复这些控制寄存器，并返回到 `kernelvec`（见 `kernel/kernelvec.S:38`）。

**kernelvec pops the saved registers from the stack and executes sret, which copies sepc to pc and resumes the interrupted kernel code.**
`kernelvec` 从栈中弹出保存的寄存器，然后执行 `sret`，把 `sepc` 的值复制到 `pc`，恢复被中断的内核代码继续执行。

---

**It’s worth thinking through how the trap return happens if kerneltrap called yield due to a timer interrupt.**
这里值得思考一个问题：如果 `kerneltrap` 是因为定时器中断而调用了 `yield`，trap 的返回过程会是怎样的？

---

**Xv6 sets a CPU’s stvec to kernelvec when that CPU enters the kernel from user space; you can see this in usertrap (kernel/trap.c:29).**
在 CPU 从用户态进入内核时，xv6 会将该 CPU 的 `stvec` 设置为 `kernelvec`；可以在 `usertrap`（见 `kernel/trap.c:29`）中看到这一点。

**There’s a window of time when the kernel has started executing but stvec is still set to uservec, and it’s crucial that no device interrupt occur during that window.**
在内核刚开始执行时，会有一个时间窗口，此时 `stvec` 仍然指向 `uservec`，在这段时间内绝对不能发生设备中断。

**Luckily the RISC-V always disables interrupts when it starts to take a trap, and usertrap doesn’t enable them again until after it sets stvec.**
幸运的是，RISC-V 在进入 trap 时总会自动关闭中断，而 `usertrap` 在设置好 `stvec` 之前也不会重新开启中断。

**4.6 Page-fault exceptions**

**Xv6’s response to exceptions is quite boring: if an exception happens in user space, the kernel kills the faulting process. If an exception happens in the kernel, the kernel panics.**
xv6 对异常的响应相当“无聊”：如果异常发生在用户空间，内核会杀死出错的进程；如果异常发生在内核，内核就会触发 panic。

**Real operating systems often respond in much more interesting ways.**
而真正的操作系统往往会以更复杂、更有趣的方式来应对。

---

**As an example, many kernels use page faults to implement copy-on-write (COW) fork.**
举个例子，许多内核利用 **缺页异常 (page fault)** 来实现 **写时复制 (Copy-on-Write, COW) fork**。

**To explain copy-on-write fork, consider xv6’s fork, described in Chapter 3.**
为了说明写时复制 fork，我们先回顾一下第 3 章中描述的 xv6 的 `fork`。

**fork causes the child’s initial memory content to be the same as the parent’s at the time of the fork.**
`fork` 会让子进程的初始内存内容与父进程在 fork 时的内容完全相同。

**Xv6 implements fork with uvmcopy (kernel/vm.c:313), which allocates physical memory for the child and copies the parent’s memory into it.**
xv6 用 `uvmcopy`（见 `kernel/vm.c:313`）来实现 `fork`，该函数为子进程分配物理内存，并把父进程的内存内容复制进去。

**It would be more efficient if the child and parent could share the parent’s physical memory.**
如果子进程和父进程能够共享父进程的物理内存，那效率会高得多。

**A straightforward implementation of this would not work, however, since it would cause the parent and child to disrupt each other’s execution with their writes to the shared stack and heap.**
然而，直接这样实现并不可行，因为父子进程会在共享的栈和堆上互相干扰。

---

**Parent and child can safely share physical memory by appropriate use of page-table permissions and page faults.**
通过恰当地使用 **页表权限** 和 **缺页异常**，父子进程可以安全地共享物理内存。

**The CPU raises a page-fault exception when a virtual address is used that has no mapping in the page table, or has a mapping whose PTE\_V flag is clear, or a mapping whose permission bits (PTE\_R, PTE\_W, PTE\_X, PTE\_U) forbid the operation being attempted.**
当访问的虚拟地址在页表中没有映射，或者映射的 **PTE\_V 标志位未设置**，或者映射的权限位（`PTE_R`、`PTE_W`、`PTE_X`、`PTE_U`）禁止当前操作时，CPU 就会触发 **缺页异常 (page fault)**。

**RISC-V distinguishes three kinds of page fault: load page faults (caused by load instructions), store page faults (caused by store instructions), and instruction page faults (caused by fetches of instructions to be executed).**
RISC-V 将缺页异常分为三类：**读缺页 (load page fault)** —— 由读指令触发；**写缺页 (store page fault)** —— 由写指令触发；**指令缺页 (instruction page fault)** —— 由取指令触发。

**The scause register indicates the type of the page fault and the stval register contains the address that couldn’t be translated.**
`scause` 寄存器指示缺页异常的类型，`stval` 寄存器保存无法翻译的虚拟地址。

---

**The basic plan in COW fork is for the parent and child to initially share all physical pages, but for each to map them read-only (with the PTE\_W flag clear).**
写时复制 fork 的基本思路是：父子进程最初共享所有物理页，但在它们的页表中将这些页映射为只读（清除 `PTE_W` 标志位）。

**Parent and child can read from the shared physical memory. If either writes a given page, the RISC-V CPU raises a page-fault exception.**
父子进程都可以读取共享的物理内存；如果其中一方试图写某一页，RISC-V CPU 就会触发缺页异常。

**The kernel’s trap handler responds by allocating a new page of physical memory and copying into it the physical page that the faulted address maps to.**
内核的 trap 处理程序会分配一页新的物理内存，并将出错地址对应的物理页内容复制过去。

**The kernel changes the relevant PTE in the faulting process’s page table to point to the copy and to allow writes as well as reads, and then resumes the faulting process at the instruction that caused the fault.**
内核接着修改出错进程页表中的相应 PTE，使其指向新复制的页，并允许读写，然后从触发缺页异常的那条指令恢复执行。

**Because the PTE now allows writes, the re-executed instruction will execute without a fault.**
由于新的 PTE 允许写操作，重新执行的那条指令将不会再触发异常。

---

**Copy-on-write requires book-keeping to help decide when physical pages can be freed, since each page can be referenced by a varying number of page tables depending on the history of forks, page faults, execs, and exits.**
写时复制需要进行一些 **引用计数的记录 (book-keeping)**，以决定物理页何时可以释放，因为每个物理页可能会被不同数量的页表引用，这取决于 fork、缺页、`exec` 和 `exit` 的历史操作。

**This book-keeping allows an important optimization: if a process incurs a store page fault and the physical page is only referred to from that process’s page table, no copy is needed.**
这种记录机制允许一个重要优化：如果进程触发写缺页，而该物理页只被该进程的页表引用，那么就不需要复制。

---

**Copy-on-write makes fork faster, since fork need not copy memory.**
写时复制让 `fork` 更快，因为它避免了立即复制内存。

**Some of the memory will have to be copied later, when written, but it’s often the case that most of the memory never has to be copied.**
虽然有些内存在之后被写入时仍需复制，但通常大部分内存从未被写过，因此不需要复制。

**A common example is fork followed by exec: a few pages may be written after the fork, but then the child’s exec releases the bulk of the memory inherited from the parent.**
一个常见例子是 **fork 之后紧跟 exec**：在 fork 之后，子进程可能会写入少量页面，但随后执行 `exec` 时会释放大部分从父进程继承的内存。

**Copy-on-write fork eliminates the need to ever copy this memory.**
写时复制 fork 完全避免了复制这些无用内存的开销。

**Furthermore, COW fork is transparent: no modifications to applications are necessary for them to benefit.**
此外，写时复制 fork 是 **透明的**：应用程序无需修改，就能从中受益。

---

**The combination of page tables and page faults opens up a wide range of interesting possibilities in addition to COW fork.**
页表和缺页异常的结合除了 COW fork，还开启了许多有趣的可能性。

**Another widely-used feature is called lazy allocation, which has two parts.**
另一种被广泛使用的特性是 **惰性分配 (lazy allocation)**，它包含两个部分：

**First, when an application asks for more memory by calling sbrk, the kernel notes the increase in size, but does not allocate physical memory and does not create PTEs for the new range of virtual addresses.**
第一，当应用程序通过调用 `sbrk` 请求更多内存时，内核仅记录大小的增加，但不会分配物理内存，也不会为新的虚拟地址范围创建 PTE。

**Second, on a page fault on one of those new addresses, the kernel allocates a page of physical memory and maps it into the page table.**
第二，当这些新地址中发生缺页异常时，内核才分配一页物理内存，并将其映射到页表中。

**Like COW fork, the kernel can implement lazy allocation transparently to applications.**
与 COW fork 一样，内核可以 **透明地** 实现惰性分配，而无需应用程序做任何改动。

---

好的，我来逐句为您翻译这段关于 **惰性分配、请求分页、换页机制** 的内容，保持技术术语准确：

---

**Since applications often ask for more memory than they need, lazy allocation is a win: the kernel doesn’t have to do any work at all for pages that the application never uses.**
由于应用程序通常会申请比实际需要更多的内存，**惰性分配 (lazy allocation)** 是一种很好的优化：对于那些应用程序从未使用过的页面，内核完全不必做任何工作。

**Furthermore, if the application is asking to grow the address space by a lot, then sbrk without lazy allocation is expensive: if an application asks for a gigabyte of memory, the kernel has to allocate and zero 262,144 4096-byte pages.**
此外，如果应用程序要求大幅扩展地址空间，而没有惰性分配的话，`sbrk` 会非常昂贵：比如应用程序申请 1GB 内存，内核必须分配并清零 262,144 个 4096 字节的页面。

**Lazy allocation allows this cost to be spread over time.**
惰性分配则可以将这部分开销分摊到未来的执行过程中。

**On the other hand, lazy allocation incurs the extra overhead of page faults, which involve a user/kernel transition.**
另一方面，惰性分配带来了额外的 **缺页异常 (page fault)** 开销，因为这需要一次用户态/内核态的切换。

**Operating systems can reduce this cost by allocating a batch of consecutive pages per page fault instead of one page and by specializing the kernel entry/exit code for such page-faults.**
操作系统可以通过优化来降低这部分开销：例如在一次缺页异常中分配一批连续的页面，而不是只分配一页，并且针对这类缺页异常优化内核的进入/退出代码。

---

**Yet another widely-used feature that exploits page faults is demand paging.**
另一种广泛使用的利用缺页异常的机制是 **请求分页 (demand paging)**。

**In exec, xv6 loads all of an application’s text and data into memory before starting the application.**
在 `exec` 中，xv6 会在启动应用程序之前，将应用程序的代码段和数据段全部加载到内存。

**Since applications can be large and reading from disk takes time, this startup cost can be noticeable to users.**
由于应用程序可能很大，而从磁盘读取数据需要时间，这种启动开销对用户来说可能相当明显。

**To decrease startup time, a modern kernel doesn’t initially load the executable file into memory, but just creates the user page table with all PTEs marked invalid.**
为了减少启动时间，现代内核不会在一开始就把可执行文件加载到内存，而只是创建用户页表，并将所有 **PTE 标记为无效**。

**The kernel starts the program running; each time the program uses a page for the first time, a page fault occurs, and in response the kernel reads the content of the page from disk and maps it into the user address space.**
内核直接启动程序；当程序第一次使用某个页面时，就会触发缺页异常，内核会从磁盘读取该页的内容，并将其映射到用户地址空间中。

**Like COW fork and lazy allocation, the kernel can implement this feature transparently to applications.**
与写时复制 fork 和惰性分配一样，请求分页对应用程序来说是 **透明的**，无需修改应用。

---

**The programs running on a computer may need more memory than the computer has RAM.**
计算机上运行的程序可能需要的内存超过物理 RAM 的容量。

**To cope gracefully, the operating system may implement paging to disk.**
为此，操作系统可能会实现 **换页到磁盘 (paging to disk)**。

**The idea is to store only a fraction of user pages in RAM, and to store the rest on disk in a paging area.**
其思想是：只把部分用户页面存放在 RAM 中，其余页面存放在磁盘的交换区。

**The kernel marks PTEs that correspond to memory stored in the paging area (and thus not in RAM) as invalid.**
内核会把对应于磁盘上页面（即不在 RAM 中）的 PTE 标记为无效。

**If an application tries to use one of the pages that has been paged out to disk, the application will incur a page fault, and the page must be paged in: the kernel trap handler will allocate a page of physical RAM, read the page from disk into the RAM, and modify the relevant PTE to point to the RAM.**
如果应用程序访问一个已经被换出到磁盘的页面，就会触发缺页异常；此时必须进行 **换入 (page-in)**：内核的 trap 处理程序会分配一个物理 RAM 页面，把该页面从磁盘读入 RAM，并修改相应的 PTE 指向 RAM。

---

**What happens if a page needs to be paged in, but there is no free physical RAM?**
那么，如果需要换入一个页面，但没有空闲的物理内存，会发生什么呢？

**In that case, the kernel must first free a physical page by paging it out or evicting it to the paging area on disk, and marking the PTEs referring to that physical page as invalid.**
这种情况下，内核必须先释放一个物理页面：要么把它换出到磁盘上的交换区，要么直接驱逐 (evict)，并将引用该物理页面的 PTE 标记为无效。

**Eviction is expensive, so paging performs best if it’s infrequent: if applications use only a subset of their memory pages and the union of the subsets fits in RAM.**
驱逐开销很大，因此换页在 **较少发生时性能最佳**：即应用程序只活跃地使用部分内存页，且这些页的总和可以放入 RAM。

**This property is often referred to as having good locality of reference.**
这种特性通常被称为具有良好的 **局部性 (locality of reference)**。

**As with many virtual memory techniques, kernels usually implement paging to disk in a way that’s transparent to applications.**
与许多虚拟内存技术一样，内核通常以对应用程序 **透明** 的方式实现换页。

---

**Computers often operate with little or no free physical memory, regardless of how much RAM the hardware provides.**
无论硬件提供多少 RAM，计算机系统常常在几乎没有空闲物理内存的情况下运行。

**For example, cloud providers multiplex many customers on a single machine to use their hardware cost-effectively.**
例如，云服务提供商会在一台机器上同时运行多个客户的任务，以提高硬件利用率。

**As another example, users run many applications on smart phones in a small amount of physical memory.**
再比如，用户会在内存很小的智能手机上运行大量应用程序。

**In such settings allocating a page may require first evicting an existing page.**
在这种场景下，分配一个新页面往往需要先驱逐一个已有页面。

**Thus, when free physical memory is scarce, allocation is expensive.**
因此，当空闲物理内存紧张时，内存分配的代价就会很高。

---

**Lazy allocation and demand paging are particularly advantageous when free memory is scarce and programs actively use only a fraction of their allocated memory.**
在空闲内存稀缺时，如果程序只活跃使用分配内存的一小部分，**惰性分配和请求分页** 尤其有优势。

**These techniques can also avoid the work wasted when a page is allocated or loaded but either never used or evicted before it can be used.**
这些技术还能避免一些无谓的开销，例如页面被分配或加载后，从未被使用，或者在使用前就被驱逐。

---

**Other features that combine paging and page-fault exceptions include automatically extending stacks and memory-mapped files, which are files that a program mapped into its address space using the mmap system call so that the program can read and write them using load and store instructions.**
其他结合 **分页** 和 **缺页异常** 的特性还包括：**自动扩展栈** 以及 **内存映射文件 (memory-mapped files)**。
所谓内存映射文件，就是程序通过 `mmap` 系统调用把文件映射到其地址空间中，这样程序就能直接通过 `load` 和 `store` 指令来读写文件。

 **4.7 Real world** 


**The trampoline and trapframe may seem excessively complex.**
trampoline 和 trapframe 的机制看起来可能显得过于复杂。

**A driving force is that the RISC-V intentionally does as little as it can when forcing a trap, to allow the possibility of very fast trap handling, which turns out to be important.**
其中的一个主要原因是：RISC-V 在强制进入 trap 时有意只做最少的工作，以便实现极快的 trap 处理，这一点在实际中非常重要。

**As a result, the first few instructions of the kernel trap handler effectively have to execute in the user environment: the user page table, and user register contents.**
因此，内核 trap 处理程序的前几条指令实际上必须在用户环境下执行：使用的是用户页表和用户寄存器内容。

**And the trap handler is initially ignorant of useful facts such as the identity of the process that’s running or the address of the kernel page table.**
而且 trap 处理程序在一开始并不知道一些有用的信息，例如当前正在运行的进程是谁，或者内核页表的地址。

**A solution is possible because RISC-V provides protected places in which the kernel can stash away information before entering user space: the sscratch register, and user page table entries that point to kernel memory but are protected by lack of PTE\_U.**
解决办法之所以可能，是因为 RISC-V 提供了几个受保护的位置，允许内核在进入用户空间之前存放信息：例如 `sscratch` 寄存器，以及那些指向内核内存但 **未设置 PTE\_U 位** 的用户页表项。

**Xv6’s trampoline and trapframe exploit these RISC-V features.**
xv6 的 trampoline 和 trapframe 就是利用了这些 RISC-V 的特性。

---

**The need for special trampoline pages could be eliminated if kernel memory were mapped into every process’s user page table (with PTE\_U clear).**
如果把内核内存映射到每个进程的用户页表中（并清除 `PTE_U`），那么就可以消除对特殊 trampoline 页的需求。

**That would also eliminate the need for a page table switch when trapping from user space into the kernel.**
这样一来，在用户态进入内核时，就不需要切换页表。

**That in turn would allow system call implementations in the kernel to take advantage of the current process’s user memory being mapped, allowing kernel code to directly dereference user pointers.**
进一步地，这样会让内核中的系统调用实现能够直接利用当前进程用户内存的映射，使得内核代码可以直接解引用用户指针。

**Many operating systems have used these ideas to increase efficiency.**
许多操作系统都使用了这些思路来提升效率。

**Xv6 avoids them in order to reduce the chances of security bugs in the kernel due to inadvertent use of user pointers, and to reduce some complexity that would be required to ensure that user and kernel virtual addresses don’t overlap.**
而 xv6 避免使用这些机制，以减少因意外使用用户指针而导致内核安全漏洞的风险，同时也避免了一些为保证用户和内核虚拟地址不重叠而带来的额外复杂性。

---

**Production operating systems implement copy-on-write fork, lazy allocation, demand paging, paging to disk, memory-mapped files, etc.**
真正的生产操作系统会实现 **写时复制 fork、惰性分配、请求分页、换页到磁盘、内存映射文件** 等机制。

**Furthermore, production operating systems try to store something useful in all areas of physical memory, typically caching file content in memory that isn’t used by processes.**
此外，生产操作系统会尽量让物理内存的每个区域都存放有用的数据，通常会把未被进程使用的内存用作 **文件内容缓存**。

---

**Production operating systems also provide applications with system calls to manage their address spaces and implement their own page-fault handling through the mmap, munmap, and sigaction system calls, as well as providing calls to pin memory into RAM (see mlock) and to advise the kernel how an application plans to use its memory (see madvise).**
生产操作系统还为应用程序提供了用于 **管理其地址空间** 的系统调用，并允许它们通过 `mmap`、`munmap` 和 `sigaction` 系统调用来实现自定义的缺页处理；此外，还提供了诸如 `mlock` 这样的系统调用，用来将内存固定在 RAM 中，以及 `madvise` 系统调用，用来让应用程序向内核提供内存使用模式的建议。
