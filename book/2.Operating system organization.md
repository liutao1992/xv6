**Operating system organization**
**操作系统的组织方式**

---

**A key requirement for an operating system is to support several activities at once.**
操作系统的一个关键要求是同时支持多个活动。

**For example, using the system call interface described in Chapter 1 a process can start new processes with fork.**
例如，使用第一章中介绍的系统调用接口，一个进程可以通过 `fork` 启动新的进程。

**The operating system must time-share the resources of the computer among these processes.**
操作系统必须在这些进程之间对计算机资源进行时间共享。

**For example, even if there are more processes than there are hardware CPUs, the operating system must ensure that all of the processes get a chance to execute.**
例如，即使进程的数量多于硬件 CPU 的数量，操作系统也必须确保所有进程都有机会执行。

**The operating system must also arrange for isolation between the processes.**
操作系统还必须为进程之间提供隔离。

**That is, if one process has a bug and malfunctions, it shouldn’t affect processes that don’t depend on the buggy process.**
也就是说，如果某个进程存在错误并发生故障，它不应该影响那些不依赖于它的其他进程。

**Complete isolation, however, is too strong, since it should be possible for processes to intentionally interact; pipelines are an example.**
然而，完全隔离又过于严格，因为进程之间应当能够有意地进行交互；管道就是一个例子。

**Thus an operating system must fulfill three requirements: multiplexing, isolation, and interaction.**
因此，一个操作系统必须满足三个要求：多路复用、隔离和交互。

---

**This chapter provides an overview of how operating systems are organized to achieve these three requirements.**
本章将概述操作系统是如何组织起来以满足这三个要求的。

**It turns out there are many ways to do so, but this text focuses on mainstream designs centered around a monolithic kernel, which is used by many Unix operating systems.**
实现这些要求的方法有很多，但本文重点关注以单体内核为中心的主流设计，这种设计被许多 Unix 操作系统采用。

**This chapter also provides an overview of an xv6 process, which is the unit of isolation in xv6, and the creation of the first process when xv6 starts.**
本章还将介绍 xv6 中的进程（它是 xv6 的隔离单位），以及 xv6 启动时第一个进程的创建过程。

---

**Xv6 runs on a multi-core RISC-V microprocessor, and much of its low-level functionality (for example, its process implementation) is specific to RISC-V.**
xv6 运行在多核 RISC-V 微处理器上，其底层功能的很大一部分（例如进程的实现）是 RISC-V 特定的。

**RISC-V is a 64-bit CPU, and xv6 is written in “LP64” C, which means long (L) and pointers (P) in the C programming language are 64 bits, but an int is 32 bits.**
RISC-V 是一个 64 位 CPU，而 xv6 是用 “LP64” C 编写的，这意味着在 C 语言中 long (L) 和指针 (P) 是 64 位，而 int 是 32 位。

**This book assumes the reader has done a bit of machine-level programming on some architecture, and will introduce RISC-V-specific ideas as they come up.**
本书假设读者已经在某种架构上做过一些底层机器级编程，并将在出现时引入 RISC-V 特有的概念。

**The user-level ISA \[2] and privileged architecture \[3] documents are the complete specifications.**
用户级 ISA \[2] 和特权架构 \[3] 文档提供了完整的规范。

**You may also refer to “The RISC-V Reader: An Open Architecture Atlas” \[15].**
你也可以参考《The RISC-V Reader: An Open Architecture Atlas》\[15]。

**The CPU in a complete computer is surrounded by support hardware, much of it in the form of I/O interfaces.**
在一台完整的计算机中，CPU 周围有许多支持硬件，其中大部分以 I/O 接口的形式存在。

**Xv6 is written for the support hardware simulated by qemu’s “-machine virt” option.**
xv6 是为 qemu 的 “-machine virt” 选项所模拟的支持硬件编写的。

**This includes RAM, a ROM containing boot code, a serial connection to the user’s keyboard/screen, and a disk for storage.**
这些硬件包括：RAM、包含启动代码的 ROM、与用户键盘/屏幕相连的串行接口，以及用于存储的磁盘。

**2.1 Abstracting physical resources**
**2.1 抽象物理资源**

---

**The first question one might ask when encountering an operating system is why have it at all?**
当人们第一次接触操作系统时，可能会提出的第一个问题是：为什么需要操作系统？

**That is, one could implement the system calls in Figure 1.2 as a library, with which applications link.**
也就是说，人们完全可以把图 1.2 中的系统调用实现为一个库，然后由应用程序进行链接使用。

**In this plan, each application could even have its own library tailored to its needs.**
在这种方案下，每个应用程序甚至可以拥有一个根据其需求定制的库。

**Applications could directly interact with hardware resources and use those resources in the best way for the application (e.g., to achieve high or predictable performance).**
应用程序可以直接与硬件资源交互，并以最适合自身的方式使用这些资源（例如，为了获得高性能或可预测的性能）。

**Some operating systems for embedded devices or real-time systems are organized in this way.**
一些嵌入式设备或实时系统的操作系统就是以这种方式组织的。

---

**The downside of this library approach is that, if there is more than one application running, the applications must be well-behaved.**
这种基于库的方法的缺点是，如果同时运行多个应用程序，那么这些应用必须“表现良好”。

**For example, each application must periodically give up the CPU so that other applications can run.**
例如，每个应用程序必须定期主动让出 CPU，以便其他应用程序能够运行。

**Such a cooperative time-sharing scheme may be OK if all applications trust each other and have no bugs.**
如果所有应用程序彼此信任，并且没有漏洞，那么这种合作式的时间共享方案可能还可以。

**It’s more typical for applications to not trust each other, and to have bugs, so one often wants stronger isolation than a cooperative scheme provides.**
但更常见的情况是，应用程序之间互不信任，而且存在漏洞，因此通常需要比合作式方案更强的隔离。

---

**To achieve strong isolation it’s helpful to forbid applications from directly accessing sensitive hardware resources, and instead to abstract the resources into services.**
为了实现强隔离，禁止应用程序直接访问敏感硬件资源是有益的，而是将这些资源抽象为服务来提供。

**For example, Unix applications interact with storage only through the file system’s open, read, write, and close system calls, instead of reading and writing the disk directly.**
例如，Unix 应用程序只能通过文件系统的 `open`、`read`、`write` 和 `close` 系统调用来访问存储，而不是直接读写磁盘。

**This provides the application with the convenience of pathnames, and it allows the operating system (as the implementer of the interface) to manage the disk.**
这为应用程序提供了使用路径名的便利，同时也使操作系统（作为接口的实现者）能够管理磁盘。

**Even if isolation is not a concern, programs that interact intentionally (or just wish to keep out of each other’s way) are likely to find a file system a more convenient abstraction than direct use of the disk.**
即使隔离不是主要考虑因素，那些需要相互交互（或只是希望互不干扰）的程序，也可能会发现文件系统比直接使用磁盘是一种更方便的抽象。

---

**Similarly, Unix transparently switches hardware CPUs among processes, saving and restoring register state as necessary, so that applications don’t have to be aware of time-sharing.**
类似地，Unix 会在进程之间透明地切换硬件 CPU，按需保存和恢复寄存器状态，这样应用程序就无需关心时间共享。

**This transparency allows the operating system to share CPUs even if some applications are in infinite loops.**
这种透明性使得操作系统即使在某些应用程序陷入无限循环时，也能实现 CPU 的共享。

---

**As another example, Unix processes use exec to build up their memory image, instead of directly interacting with physical memory.**
再举一个例子，Unix 进程使用 `exec` 来构建它们的内存镜像，而不是直接操作物理内存。

**This allows the operating system to decide where to place a process in memory; if memory is tight, the operating system might even store some of a process’s data on disk.**
这使得操作系统可以决定将进程放置在内存的哪个位置；如果内存紧张，操作系统甚至可以把部分进程数据存放到磁盘上。

**exec also provides users with the convenience of a file system to store executable program images.**
`exec` 还为用户提供了使用文件系统存储可执行程序镜像的便利。

---

**Many forms of interaction among Unix processes occur via file descriptors.**
Unix 进程之间的许多交互形式都是通过文件描述符实现的。

**Not only do file descriptors abstract away many details (e.g., where data in a pipe or file is stored), they are also defined in a way that simplifies interaction.**
文件描述符不仅屏蔽了许多底层细节（例如，管道或文件中的数据存放位置），而且其定义方式也简化了进程之间的交互。

**For example, if one application in a pipeline fails, the kernel generates an end-of-file signal for the next process in the pipeline.**
例如，如果管道中的一个应用程序失败，内核会为下一个管道进程生成一个“文件结束”（EOF）信号。

---

**The system-call interface in Figure 1.2 is carefully designed to provide both programmer convenience and the possibility of strong isolation.**
图 1.2 中的系统调用接口经过精心设计，既为程序员提供了便利，又保证了强隔离的可能性。

**The Unix interface is not the only way to abstract resources, but it has proved to be a good one.**
Unix 接口并不是抽象资源的唯一方式，但事实证明它是一种行之有效的方式。

**2.2 User mode, supervisor mode, and system calls**
**2.2 用户模式、管理者模式和系统调用**

---

**Strong isolation requires a hard boundary between applications and the operating system.**
强隔离要求在应用程序和操作系统之间建立一个严格的边界。

**If the application makes a mistake, we don’t want the operating system to fail or other applications to fail.**
如果某个应用程序出错，我们不希望操作系统因此崩溃，也不希望其他应用程序受到影响。

**Instead, the operating system should be able to clean up the failed application and continue running other applications.**
相反，操作系统应该能够清理出错的应用程序，并继续运行其他应用程序。

**To achieve strong isolation, the operating system must arrange that applications cannot modify (or even read) the operating system’s data structures and instructions and that applications cannot access other processes’ memory.**
为了实现强隔离，操作系统必须确保：应用程序不能修改（甚至不能读取）操作系统的数据结构和指令，并且应用程序不能访问其他进程的内存。

---

**CPUs provide hardware support for strong isolation.**
CPU 提供了实现强隔离的硬件支持。

**For example, RISC-V has three modes in which the CPU can execute instructions: machine mode, supervisor mode, and user mode.**
例如，RISC-V 提供三种 CPU 执行指令的模式：机器模式（machine mode）、管理者模式（supervisor mode）、用户模式（user mode）。

**Instructions executing in machine mode have full privilege; a CPU starts in machine mode.**
在机器模式下执行的指令拥有完全的特权；CPU 启动时会进入机器模式。

**Machine mode is mostly intended for setting up the computer during boot.**
机器模式主要用于计算机启动时的初始化设置。

**Xv6 executes a few lines in machine mode and then changes to supervisor mode.**
xv6 在机器模式下执行少量代码后，就会切换到管理者模式。

---

**In supervisor mode the CPU is allowed to execute privileged instructions: for example, enabling and disabling interrupts, reading and writing the register that holds the address of a page table, etc.**
在管理者模式下，CPU 可以执行特权指令，例如：启用或禁用中断、读写保存页表地址的寄存器等。

**If an application in user mode attempts to execute a privileged instruction, then the CPU doesn’t execute the instruction, but switches to supervisor mode so that supervisor-mode code can terminate the application, because it did something it shouldn’t be doing.**
如果用户模式下的应用程序试图执行特权指令，CPU 不会执行该指令，而是切换到管理者模式，让管理者模式下的代码终止该应用程序，因为它做了不该做的事情。

**Figure 1.1 in Chapter 1 illustrates this organization.**
第一章的图 1.1 展示了这种组织结构。

**An application can execute only user-mode instructions (e.g., adding numbers, etc.) and is said to be running in user space, while the software in supervisor mode can also execute privileged instructions and is said to be running in kernel space.**
应用程序只能执行用户模式指令（例如，加法运算等），这被称为运行在用户空间；而管理者模式下的软件还可以执行特权指令，这被称为运行在内核空间。

**The software running in kernel space (or in supervisor mode) is called the kernel.**
运行在内核空间（或管理者模式下）的软件被称为内核（kernel）。

---

**An application that wants to invoke a kernel function (e.g., the read system call in xv6) must transition to the kernel; an application cannot invoke a kernel function directly.**
想要调用内核函数（例如 xv6 中的 `read` 系统调用）的应用程序，必须通过切换进入内核；应用程序不能直接调用内核函数。

**CPUs provide a special instruction that switches the CPU from user mode to supervisor mode and enters the kernel at an entry point specified by the kernel. (RISC-V provides the ecall instruction for this purpose.)**
CPU 提供了一条特殊指令，可以将 CPU 从用户模式切换到管理者模式，并进入内核预先指定的入口点。（RISC-V 提供的 `ecall` 指令就是用于此目的的。）

**Once the CPU has switched to supervisor mode, the kernel can then validate the arguments of the system call (e.g., check if the address passed to the system call is part of the application’s memory), decide whether the application is allowed to perform the requested operation (e.g., check if the application is allowed to write the specified file), and then deny it or execute it.**
一旦 CPU 切换到管理者模式，内核就可以验证系统调用的参数（例如，检查传递给系统调用的地址是否属于应用程序的内存），决定应用程序是否被允许执行所请求的操作（例如，检查应用程序是否有权写入指定文件），然后决定拒绝还是执行该操作。

**It is important that the kernel control the entry point for transitions to supervisor mode; if the application could decide the kernel entry point, a malicious application could, for example, enter the kernel at a point where the validation of arguments is skipped.**
关键在于，必须由内核控制进入管理者模式的入口点；如果应用程序能自己决定入口点，那么恶意应用程序可能会选择跳过参数验证的入口位置，从而破坏系统安全。

**2.3 Kernel organization**
**2.3 内核的组织方式**

---

**A key design question is what part of the operating system should run in supervisor mode.**
一个关键的设计问题是：操作系统的哪些部分应该在管理者模式下运行。

**One possibility is that the entire operating system resides in the kernel, so that the implementations of all system calls run in supervisor mode.**
一种可能的做法是：整个操作系统都驻留在内核中，这样所有系统调用的实现都在管理者模式下运行。

**This organization is called a monolithic kernel.**
这种组织方式称为 **单体内核（monolithic kernel）**。

---

**In this organization the entire operating system consists of a single program running with full hardware privilege.**
在这种组织方式中，整个操作系统由一个在完全硬件特权下运行的单一程序组成。

**This organization is convenient because the OS designer doesn’t have to decide which parts of the operating system don’t need full hardware privilege.**
这种方式很方便，因为操作系统的设计者不需要区分哪些部分需要完全硬件特权，哪些部分不需要。

**Furthermore, it is easier for different parts of the operating system to cooperate.**
此外，操作系统的不同部分更容易相互协作。

**For example, an operating system might have a buffer cache that can be shared both by the file system and the virtual memory system.**
例如，一个操作系统可能有一个缓冲区缓存（buffer cache），既可以被文件系统使用，也可以被虚拟内存系统使用。

![Figure 2.1: A microkernel with a file-system server](./img/截屏2025-08-23%2016.57.28.png)

---

**A downside of the monolithic organization is that the interactions among different parts of the operating system are often complex (as we will see in the rest of this text), and therefore it is easy for an operating system developer to make a mistake.**
单体内核的一个缺点是：操作系统不同部分之间的交互通常很复杂（我们将在后续内容中看到），因此操作系统开发者很容易出错。

**In a monolithic kernel, a mistake is fatal, because an error in supervisor mode will often cause the kernel to fail.**
在单体内核中，错误往往是致命的，因为管理者模式下的错误通常会导致整个内核失败。

**If the kernel fails, the computer stops working, and thus all applications fail too. The computer must reboot to start again.**
如果内核崩溃，计算机就会停止工作，所有应用程序也会随之失败。此时必须重启计算机才能重新运行。

---

**To reduce the risk of mistakes in the kernel, OS designers can minimize the amount of operating system code that runs in supervisor mode, and execute the bulk of the operating system in user mode.**
为了降低内核中出错的风险，操作系统设计者可以尽量减少在管理者模式下运行的代码量，而将大部分操作系统放在用户模式下运行。

**This kernel organization is called a microkernel.**
这种内核组织方式称为 **微内核（microkernel）**。

---

**Figure 2.1 illustrates this microkernel design. In the figure, the file system runs as a user-level process.**
图 2.1 展示了微内核的设计。在图中，文件系统作为一个用户级进程运行。

**OS services running as processes are called servers.**
以进程形式运行的操作系统服务称为 **服务器（servers）**。

**To allow applications to interact with the file server, the kernel provides an inter-process communication mechanism to send messages from one user-mode process to another.**
为了让应用程序能够与文件服务器交互，内核提供了一种 **进程间通信机制（IPC）**，用于在一个用户模式进程和另一个用户模式进程之间传递消息。

**For example, if an application like the shell wants to read or write a file, it sends a message to the file server and waits for a response.**
例如，如果一个类似 shell 的应用程序想要读写文件，它会向文件服务器发送一条消息，并等待响应。

---

**In a microkernel, the kernel interface consists of a few low-level functions for starting applications, sending messages, accessing device hardware, etc.**
在微内核中，内核接口只包含少量的底层功能，例如启动应用程序、发送消息、访问设备硬件等。

**This organization allows the kernel to be relatively simple, as most of the operating system resides in user-level servers.**
这种组织方式使得内核相对简单，因为大部分操作系统功能都位于用户级服务器中。

---

**In the real world, both monolithic kernels and microkernels are popular.**
在现实世界中，单体内核和微内核都很流行。

**Many Unix kernels are monolithic.**
许多 Unix 内核是单体内核。

**For example, Linux has a monolithic kernel, although some OS functions run as user-level servers (e.g., the window system).**
例如，Linux 采用单体内核，尽管某些操作系统功能（如窗口系统）是作为用户级服务器运行的。

**Linux delivers high performance to OS-intensive applications, partially because the subsystems of the kernel can be tightly integrated.**
Linux 能为操作系统密集型应用程序提供高性能，部分原因是其内核子系统可以紧密集成。

---

**Operating systems such as Minix, L4, and QNX are organized as a microkernel with servers, and have seen wide deployment in embedded settings.**
像 Minix、L4 和 QNX 这样的操作系统是基于微内核和服务器的组织方式，并且在嵌入式环境中得到了广泛应用。

**A variant of L4, seL4, is small enough that it has been verified for memory safety and other security properties \[8].**
L4 的一个变种 **seL4** 小到足以被正式验证其内存安全性和其他安全特性 \[8]。

---

**There is much debate among developers of operating systems about which organization is better, and there is no conclusive evidence one way or the other.**
在操作系统开发者之间，关于哪种组织方式更好一直存在大量争论，但没有确凿的证据表明哪一种更优。

**Furthermore, it depends much on what “better” means: faster performance, smaller code size, reliability of the kernel, reliability of the complete operating system (including user-level services), etc.**
此外，“更好”的含义本身也取决于具体标准：是性能更快、代码规模更小、内核更可靠，还是整个操作系统（包括用户级服务）更可靠。

---

**There are also practical considerations that may be more important than the question of which organization.**
还有一些实际因素可能比选择哪种组织方式更重要。

**Some operating systems have a microkernel but run some of the user-level services in kernel space for performance reasons.**
有些操作系统采用微内核，但出于性能考虑，会在内核空间中运行部分用户级服务。

**Some operating systems have monolithic kernels because that is how they started and there is little incentive to move to a pure microkernel organization, because new features may be more important than rewriting the existing operating system to fit a microkernel design.**
有些操作系统采用单体内核，是因为它们最初就是这样设计的，而且几乎没有动力去迁移到纯粹的微内核组织方式，因为开发新特性可能比重写现有操作系统以适应微内核设计更重要。

由于 xv6 并未提供太多服务，它的内核比某些微内核还要小，但从概念上讲，xv6 属于单体内核。

### 2.5 进程概览

The unit of isolation in xv6 (as in other Unix operating systems) is a process. The process abstraction prevents one process from wrecking or spying on another process’s memory, CPU, file descriptors, etc. It also prevents a process from wrecking the kernel itself, so that a process can’t subvert the kernel’s isolation mechanisms. The kernel must implement the process abstraction with care because a buggy or malicious application may trick the kernel or hardware into doing something bad (e.g., circumventing isolation). The mechanisms used by the kernel to implement processes include the user/supervisor mode flag, address spaces, and time-slicing of threads.

在 xv6（和其他 Unix 操作系统一样）中，隔离的基本单位是进程。进程抽象能防止一个进程破坏或窥探另一个进程的内存、CPU、文件描述符等。同时，它也能防止进程破坏内核本身，从而避免进程颠覆内核的隔离机制。内核必须谨慎地实现进程抽象，因为一个有漏洞或恶意的应用程序可能会诱使内核或硬件做出危险的事情（例如绕过隔离）。内核实现进程所依赖的机制包括用户/管理者模式标志、地址空间以及线程的时间片轮转。

---

To help enforce isolation, the process abstraction provides the illusion to a program that it has its own private machine. A process provides a program with what appears to be a private memory system, or address space, which other processes cannot read or write. A process also provides the program with what appears to be its own CPU to execute the program’s instructions.

为了加强隔离，进程抽象向程序提供了一种“拥有独立机器”的假象。进程为程序提供了一个看似独立的内存系统或地址空间，其他进程无法读写其中的内容。同时，进程还向程序提供了一个看似独立的 CPU，用于执行该程序的指令。

---

Xv6 uses page tables (which are implemented by hardware) to give each process its own address space. The RISC-V page table translates (or “maps”) a virtual address (the address that an RISC-V instruction manipulates) to a physical address (an address that the CPU sends to main memory).

Xv6 使用页表（由硬件实现）为每个进程提供独立的地址空间。RISC-V 页表会将虚拟地址（即 RISC-V 指令操作的地址）转换（或“映射”）为物理地址（CPU 发送到主内存的地址）。

---

Xv6 maintains a separate page table for each process that defines that process’s address space. As illustrated in Figure 2.3, an address space includes the process’s user memory starting at virtual address zero. Instructions come first, followed by global variables, then the stack, and finally a “heap” area (for malloc) that the process can expand as needed.

Xv6 为每个进程维护一个独立的页表，用来定义该进程的地址空间。如图 2.3 所示，一个地址空间包含从虚拟地址 0 开始的用户内存。最前面是指令段，其后是全局变量，然后是栈，最后是一个“堆”区域（用于 malloc），进程可根据需要扩展该区域。

---

There are a number of factors that limit the maximum size of a process’s address space: pointers on the RISC-V are 64 bits wide; the hardware uses only the low 39 bits when looking up virtual addresses in page tables; and xv6 uses only 38 of those 39 bits. Thus, the maximum address is 2³⁸ − 1 = 0x3fffffffff, which is MAXVA (kernel/riscv.h:378).

有若干因素限制了进程地址空间的最大大小：在 RISC-V 中，指针宽度为 64 位；硬件在查找页表时只使用低 39 位；而 xv6 实际上只使用其中的 38 位。因此，最大地址为 2³⁸ − 1 = 0x3fffffffff，即 MAXVA（kernel/riscv.h:378）。

---

At the top of the address space xv6 places a trampoline page (4096 bytes) and a trapframe page. Xv6 uses these two pages to transition into the kernel and back; the trampoline page contains the code to transition in and out of the kernel, and the trapframe is where the kernel saves the process’s user registers, as Chapter 4 explains.

在地址空间的顶端，xv6 放置了一个跳板页（4096 字节）和一个陷阱帧页。xv6 使用这两个页面完成进程进入内核和返回的切换；跳板页包含了进出内核的切换代码，而陷阱帧则是内核保存进程用户寄存器的地方，相关细节在第 4 章中会解释。

---

Xv6 keeps track of a process’s address space with a page table, as well as other information about the process, in a `struct proc` (kernel/proc.h:86). Each process has a thread of execution (or just thread) that executes the process’s instructions. A thread can be suspended and later resumed. The state of a thread — the contents of registers, the program counter, and the stack — is called the thread’s context. A process’s thread is context-switched in and out by the kernel.

xv6 使用页表来跟踪进程的地址空间，并在 `struct proc`（kernel/proc.h:86）中记录进程的其他信息。每个进程都拥有一个执行线程（简称线程），用于执行该进程的指令。线程可以被挂起，也可以在之后恢复。线程的状态——寄存器内容、程序计数器和栈——被称为线程上下文。进程的线程由内核进行上下文切换。

---

At any given time, one thread per CPU is executing in kernel mode, in the kernel’s address space. This kernel thread can execute either user instructions on behalf of a process, or kernel instructions. A transition from user space to kernel space occurs when a process makes a system call, or when the hardware raises an interrupt or exception. The kernel thread resumes executing user instructions when it returns from the system call, interrupt, or exception.

在任意时刻，每个 CPU 上都会有一个线程在内核模式下执行，并运行在内核的地址空间中。这个内核线程既可以代表某个进程执行用户指令，也可以执行内核指令。当进程发起系统调用，或当硬件触发中断或异常时，就会发生从用户空间到内核空间的切换。当系统调用、中断或异常处理完成后，内核线程会恢复执行用户指令。

---

To switch between processes, xv6 performs a context switch: it saves the state of the currently running process (its thread’s registers and stack) and restores the state of a previously suspended process. This allows multiple processes to share the CPUs while giving the illusion that each has its own dedicated CPU.

为了在进程之间切换，xv6 会执行上下文切换：保存当前运行进程的状态（其线程的寄存器和栈），并恢复之前被挂起进程的状态。这样，多个进程可以共享 CPU，同时给人一种每个进程都独占 CPU 的假象。

---

Each process also has its own set of file descriptors. A file descriptor is an index into a per-process table that the kernel maintains. This table maps file descriptors to open files. When a process performs a system call like `read` or `write`, it specifies a file descriptor, and the kernel uses the process’s table to find the corresponding file.

每个进程还拥有自己的一组文件描述符。文件描述符是一个索引，指向内核为该进程维护的一个表格。该表将文件描述符映射到打开的文件。当进程执行 `read` 或 `write` 这样的系统调用时，它会指定一个文件描述符，内核则利用进程的表来找到对应的文件。

---

A process’s private resources include its virtual address space and file descriptor table. Resources shared among processes include the disk, the console, and physical memory. The kernel must mediate access to these shared resources to provide isolation and fairness.

进程的私有资源包括它的虚拟地址空间和文件描述符表。而进程之间共享的资源包括磁盘、控制台和物理内存。内核必须在这些共享资源的访问中起到仲裁作用，以保证隔离性和公平性。

---

When a process makes a system call, the hardware switches from user mode to kernel mode and starts executing in the kernel. To resume the process later, the kernel must save the process’s user registers, so that it can restore them and return to user space. Xv6 uses a per-process trapframe structure to save these registers (kernel/proc.h:41). The kernel fills in the trapframe when a system call, interrupt, or exception occurs, and restores the trapframe when returning to user space.

当一个进程发起系统调用时，硬件会从用户模式切换到内核模式，并开始在内核中执行。为了之后能够恢复进程，内核必须保存该进程的用户寄存器，以便在返回用户空间时能够恢复。xv6 使用每个进程专有的 trapframe 结构体来保存这些寄存器（kernel/proc.h:41）。当系统调用、中断或异常发生时，内核会填写 trapframe；当返回用户空间时，内核则会恢复 trapframe 的内容。

---

Because the kernel uses its own stack (separate from the user stack), the trapframe must be accessible both when executing in kernel mode and when restoring user mode state. To achieve this, xv6 places the trapframe just below the top of the kernel stack for each process. This allows the kernel to access the trapframe easily while the process is running in the kernel.

由于内核使用自己的栈（与用户栈分离），trapframe 必须在内核模式执行和恢复用户模式状态时都可访问。为此，xv6 将 trapframe 放置在每个进程的内核栈顶部之下。这样，在进程运行于内核时，内核就能方便地访问 trapframe。

---

To return from a system call (or interrupt/exception), the kernel copies the values from the process’s trapframe back into the CPU registers, switches to user mode, and resumes executing at the instruction following the system call. This mechanism ensures that the process continues execution as if the system call were just a function call.

在系统调用（或中断/异常）返回时，内核会将进程 trapframe 中保存的值拷贝回 CPU 寄存器，然后切换回用户模式，并在系统调用之后的那条指令继续执行。这样，进程的执行就好像系统调用只是一次普通的函数调用一样。

---

The code that performs this transition between user space and kernel space is called the trampoline (kernel/trampoline.S). The trampoline code runs in both directions: when entering the kernel from user space, and when returning to user space from the kernel. It is written in assembly because it must manipulate low-level CPU state directly.

负责用户空间与内核空间切换的代码称为 trampoline（kernel/trampoline.S）。trampoline 代码在两个方向上都运行：从用户空间进入内核，以及从内核返回用户空间。它用汇编编写，因为必须直接操作底层的 CPU 状态。

After the trampoline saves the user registers in the trapframe and switches to the kernel stack, it jumps to a common kernel entry point. The kernel entry point calls the system call dispatcher, which examines the system call number and arguments (stored in the trapframe) and invokes the corresponding kernel function.

The kernel function executes on the kernel stack, using kernel data structures and performing privileged operations as needed. The function can access the process’s address space through the page table. Once the kernel function finishes, it writes the return value back into the trapframe.

内核函数在内核栈上执行，根据需要使用内核数据结构并执行特权操作。函数可以通过页表访问进程的地址空间。一旦内核函数完成，它会将返回值写回到 trapframe 中。

Finally, the trampoline code restores the CPU registers from the trapframe, switches back to user mode, and resumes execution of the process at the instruction following the system call. The process sees no difference compared with a normal function call, aside from the fact that it may have temporarily yielded the CPU to other processes.

最后，trampoline 代码从 trapframe 恢复 CPU 寄存器，切换回用户模式，并在系统调用后的指令处继续执行进程。除了可能暂时将 CPU 让给其他进程外，进程不会感受到与普通函数调用有任何不同。

---

A process can also block in the kernel while waiting for I/O. When the I/O completes, the kernel can resume the process at the point where it left off. This blocking mechanism allows the CPU to be shared efficiently among multiple processes.

进程在等待 I/O 时也可以在内核中被阻塞。当 I/O 完成后，内核可以从进程中断的位置恢复执行。这种阻塞机制允许多个进程高效地共享 CPU。

---

p->state indicates whether the process is allocated, ready to run, currently running on a CPU, waiting for I/O, or exiting.

p->state 指示进程的状态：已分配、可运行、正在 CPU 上运行、等待 I/O 或正在退出。

---

p->pagetable holds the process’s page table, in the format that the RISC-V hardware expects. Xv6 causes the paging hardware to use a process’s p->pagetable when executing that process in user space. A process’s page table also serves as the record of the addresses of the physical pages allocated to store the process’s memory.

p->pagetable 保存进程的页表，以 RISC-V 硬件期望的格式存储。xv6 会在用户空间执行该进程时，让分页硬件使用这个页表。进程的页表同时也记录了为存储该进程内存而分配的物理页的地址。

---

In summary, a process bundles two design ideas: an address space to give a process the illusion of its own memory, and a thread to give the process the illusion of its own CPU. In xv6, a process consists of one address space and one thread. In real operating systems a process may have more than one thread to take advantage of multiple CPUs.

总的来说，进程包含了两个设计思想：一个地址空间，为进程提供独立内存的假象；一个线程，为进程提供独立 CPU 的假象。在 xv6 中，一个进程由一个地址空间和一个线程组成。在实际操作系统中，进程可能包含多个线程，以利用多核 CPU 的能力。

The function start performs some configuration that is only allowed in machine mode, and then switches to supervisor mode. To enter supervisor mode, RISC-V provides the instruction mret. This instruction is most often used to return from a previous call from supervisor mode to machine mode. start isn’t returning from such a call, but sets things up as if it were: it sets the previous privilege mode to supervisor in the register mstatus, it sets the return address to main by writing main’s address into the register mepc, disables virtual address translation in supervisor mode by writing 0 into the page-table register satp, and delegates all interrupts and exceptions to supervisor mode.

在进入管理者模式之前，`start` 还要完成一项任务：配置时钟芯片以产生定时器中断。完成这些准备工作后，`start` 调用 `mret` “返回”到管理者模式。此时，程序计数器（PC）会跳转到 **main**（kernel/main.c:11），也就是之前写入 **mepc** 的地址。

在 **main**（kernel/main.c:11）初始化若干设备和子系统后，它会调用 **userinit**（kernel/proc.c:233）创建第一个进程。第一个进程执行一个用 RISC-V 汇编编写的小程序，该程序发起 xv6 中的第一个系统调用。**initcode.S**（user/initcode.S:3）将 `exec` 系统调用号 **SYS\_EXEC**（kernel/syscall.h:8）加载到寄存器 **a7**，然后调用 **ecall** 重新进入内核。

The system call table (kernel/syscall.c:107) maps SYS\_EXEC to the function sys\_exec, which the kernel invokes. As we saw in Chapter 1, exec replaces the memory and registers of the current process with a new program (in this case, /init).

内核在 **syscall**（kernel/syscall.c:132）中使用寄存器 **a7** 中的系统调用号来调用所需的系统调用。系统调用表（kernel/syscall.c:107）将 **SYS\_EXEC** 映射到函数 **sys\_exec**，内核随后调用该函数。正如第 1 章所述，**exec** 会用一个新程序（此处为 **/init**）替换当前进程的内存和寄存器。

当内核完成 **exec** 后，它会返回用户空间，运行 **/init** 进程。**init**（user/init.c:15）在需要时创建一个新的控制台设备文件，并将其打开为文件描述符 **0、1、2**。然后它在控制台上启动一个 **shell**。至此，系统启动完成。

### 2.7 Security Model
---

You may wonder how the operating system deals with buggy or malicious code. Because coping with malice is strictly harder than dealing with accidental bugs, it’s reasonable to focus mostly on providing security against malice. Here’s a high-level view of typical security assumptions and goals in operating system design.

你可能会想，操作系统是如何应对有缺陷或恶意的代码的。因为处理恶意攻击比处理偶然的错误要困难得多，所以操作系统设计中更合理的做法是着重考虑防御恶意行为。下面是操作系统设计中典型的安全假设与目标的高层次概览。

---

The operating system must assume that a process’s user-level code will do its best to wreck the kernel or other processes. User code may try to dereference pointers outside its allowed address space; it may attempt to execute any RISC-V instructions, even those not intended for user code; it may try to read and write any RISC-V control register; it may try to directly access device hardware; and it may pass clever values to system calls in an attempt to trick the kernel into crashing or doing something stupid.

操作系统必须假设进程的用户级代码会竭尽全力破坏内核或其他进程。用户代码可能尝试解引用超出其允许地址空间的指针；可能尝试执行任意 RISC-V 指令（甚至是那些不应当由用户代码执行的指令）；可能尝试读写任意 RISC-V 控制寄存器；可能试图直接访问设备硬件；还可能通过向系统调用传递巧妙的参数，诱使内核崩溃或执行愚蠢的操作。

---

The kernel’s goal is to restrict each user processes so that all it can do is read/write/execute its own user memory, use the 32 general-purpose RISC-V registers, and affect the kernel and other processes in the ways that system calls are intended to allow. The kernel must prevent any other actions. This is typically an absolute requirement in kernel design.

内核的目标是将每个用户进程限制在严格范围内，使其只能读/写/执行自己的用户内存、使用 RISC-V 的 32 个通用寄存器，并且只能通过系统调用所允许的方式影响内核和其他进程。内核必须阻止所有其他行为。这通常是内核设计中的绝对要求。

---

The expectations for the kernel’s own code are quite different. Kernel code is assumed to be written by well-meaning and careful programmers. Kernel code is expected to be bug-free, and certainly to contain nothing malicious. This assumption affects how we analyze kernel code. For example, there are many internal kernel functions (e.g., the spin locks) that would cause serious problems if kernel code used them incorrectly. When examining any specific piece of kernel code, we’ll want to convince ourselves that it behaves correctly. We assume, however, that kernel code in general is correctly written, and follows all the rules about use of the kernel’s own functions and data structures. At the hardware level, the RISC-V CPU, RAM, disk, etc. are assumed to operate as advertised in the documentation, with no hardware bugs.

对内核代码的期望则完全不同。内核代码通常被假设为由善意且谨慎的程序员编写的，应该没有 bug，更不可能包含恶意代码。这一假设会影响我们分析内核代码的方式。例如，内核内部的许多函数（如自旋锁）如果被错误使用会引发严重问题。在检查任何特定的内核代码时，我们需要确认其行为正确。然而，我们总体上假设内核代码是正确编写的，并且遵循所有使用内核函数和数据结构的规则。在硬件层面，RISC-V 的 CPU、内存、磁盘等也被假设为按照文档描述工作，不存在硬件缺陷。

---

Of course in real life things are not so straightforward. It’s difficult to prevent clever user code from making a system unusable (or causing it to panic) by consuming kernel-protected resources – disk space, CPU time, process table slots, etc. It’s usually impossible to write bug-free kernel code or design bug-free hardware; if the writers of malicious user code are aware of kernel or hardware bugs, they will exploit them. Even in mature, widely-used kernels, such as Linux, people discover new vulnerabilities continuously \[1].

当然，在现实中情况并没有这么简单。很难防止聪明的用户代码通过消耗受内核保护的资源（磁盘空间、CPU 时间、进程表项等）来让系统变得不可用（或导致系统 panic）。几乎不可能编写完全无 bug 的内核代码或设计无缺陷的硬件；如果恶意代码编写者知道内核或硬件的漏洞，他们一定会加以利用。即便是在成熟且被广泛使用的内核（如 Linux）中，人们仍然不断发现新的漏洞 \[1]。

---

It’s worthwhile to design safeguards into the kernel against the possibility that it has bugs: assertions, type checking, stack guard pages, etc. Finally, the distinction between user and kernel code is sometimes blurred: some privileged user-level processes may provide essential services and effectively be part of the operating system, and in some operating systems privileged user code can insert new code into the kernel (as with Linux’s loadable kernel modules).

因此，在内核中设计一些防护措施来对抗可能存在的 bug 是值得的：例如断言、类型检查、栈保护页等。最后，用户代码与内核代码之间的界限有时也会模糊：一些具有特权的用户级进程可能会提供关键服务，从而实际上成为操作系统的一部分；而在某些操作系统中，特权用户代码甚至可以向内核插入新代码（如 Linux 的可加载内核模块）。

---

### 2.8 Real world

Most operating systems have adopted the process concept, and most processes look similar to xv6’s.

大多数操作系统都采用了进程的概念，而且大多数进程的实现方式都与 xv6 的进程相似。

---

Modern operating systems, however, support several threads within a process, to allow a single process to exploit multiple CPUs.

然而，现代操作系统支持在一个进程中运行多个线程，这样单个进程就可以利用多个 CPU。

---

Supporting multiple threads in a process involves quite a bit of machinery that xv6 doesn’t have, often including interface changes (e.g., Linux’s clone, a variant of fork), to control which aspects of a process threads share.

在一个进程中支持多个线程需要相当多的机制，而这些是 xv6 不具备的，通常还涉及接口上的改变（例如 Linux 的 `clone`，它是 `fork` 的一种变体），以便控制线程之间共享进程的哪些部分。
