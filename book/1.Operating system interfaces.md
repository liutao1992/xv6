### 1.1 Operating system interfaces（操作系统接口）

---

The job of an operating system is to share a computer among multiple programs and to provide a more useful set of services than the hardware alone supports. An operating system manages and abstracts the low-level hardware, so that, for example, a word processor need not concern itself with which type of disk hardware is being used. An operating system shares the hardware among multiple programs so that they run (or appear to run) at the same time. Finally, operating systems provide controlled ways for programs to interact, so that they can share data or work together.

操作系统的工作是让多程序共享一台计算机，并且提供比硬件本身支持的功能更有用的一组服务。操作系统管理并抽象底层硬件，例如，文字处理软件不必关心所使用的磁盘硬件类型。操作系统在多个程序之间共享硬件，使它们能够（或者看起来能够）同时运行。最后，操作系统为程序之间的交互提供受控的方式，使它们能够共享数据或协同工作。

---

An operating system provides services to user programs through an interface. Designing a good interface turns out to be difficult. On the one hand, we would like the interface to be simple and narrow because that makes it easier to get the implementation right. On the other hand, we may be tempted to offer many sophisticated features to applications. The trick in resolving this tension is to design interfaces that rely on a few mechanisms that can be combined to provide much generality.

操作系统通过接口向用户程序提供服务。事实证明，设计一个好的接口并不容易。一方面，我们希望接口尽可能简单、精炼，因为这样更容易实现正确；另一方面，我们又想要为应用程序提供许多复杂的功能。解决这一矛盾的诀窍是设计依赖于少数机制的接口，但这些机制可以组合起来，提供很强的通用性。

---

This book uses a single operating system as a concrete example to illustrate operating system concepts. That operating system, xv6, provides the basic interfaces introduced by Ken Thompson and Dennis Ritchie’s Unix operating system \[17], as well as mimicking Unix’s internal design.

本书使用一个操作系统作为具体示例来讲解操作系统概念。这个操作系统是 xv6，它提供了 Ken Thompson 和 Dennis Ritchie 的 Unix 操作系统 \[17] 中引入的基本接口，并且模仿了 Unix 的内部设计。

---

Unix provides a narrow interface whose mechanisms combine well, offering a surprising degree of generality. This interface has been so successful that modern operating systems—BSD, Linux, macOS, Solaris, and even, to a lesser extent, Microsoft Windows—have Unix-like interfaces. Understanding xv6 is a good start toward understanding any of these systems and many others.

Unix 提供了一套精简的接口，其各项机制能够良好地协同，从而展现出出人意料的通用性。这个接口极为成功，以至于现代操作系统——BSD、Linux、macOS、Solaris，甚至在较小程度上还有微软的 Windows——都拥有类 Unix 的接口。理解 xv6 是理解这些系统以及许多其他系统的良好起点。

---

As Figure 1.1 shows, xv6 takes the traditional form of a kernel, a special program that provides services to running programs. Each running program, called a process, has memory containing instructions, data, and a stack. The instructions implement the program’s computation. The data are the variables on which the computation acts. The stack organizes the program’s procedure calls. A given computer typically has many processes but only a single kernel.

![图 1.1](./img/截屏2025-08-24%2010.11.52.png)


如图 1.1 所示，xv6 采用传统的内核形式，即一个为正在运行的程序提供服务的特殊程序。每个正在运行的程序称为 **进程**，它的内存包含指令、数据和栈。指令实现程序的计算；数据是计算所作用的变量；栈则用来组织程序的过程调用。通常情况下，一台计算机上会有多个进程，但只有一个内核。

---

When a process needs to invoke a kernel service, it invokes a system call, one of the calls in the operating system’s interface. The system call enters the kernel; the kernel performs the service and returns. Thus a process alternates between executing in user space and kernel space.

当一个进程需要调用内核服务时，它会调用系统调用，这是操作系统接口中的函数调用之一。系统调用进入内核；内核执行该服务并返回。因此，进程会在用户空间和内核空间之间交替运行。

---

As described in detail in subsequent chapters, the kernel uses the hardware protection mechanisms provided by a CPU to ensure that each process executing in user space can access only its own memory. The kernel executes with the hardware privileges required to implement these protections; user programs execute without those privileges. When a user program invokes a system call, the hardware raises the privilege level and starts executing a pre-arranged function in the kernel.

正如后续章节中详细描述的那样，内核利用 CPU 提供的硬件保护机制来确保每个在用户空间执行的进程只能访问属于它自己的内存。内核在具有实现这些保护所需的硬件特权的状态下执行；而用户程序在没有这些特权的状态下运行。当用户程序调用系统调用时，硬件会提升特权级别，并开始执行内核中预先安排好的函数。

内核所提供的系统调用集合就是用户程序所看到的接口。xv6 内核提供了传统 Unix 内核服务与系统调用的一个子集。图 1.2 列出了 xv6 的所有系统调用。

The rest of this chapter outlines xv6’s services—processes, memory, file descriptors, pipes, and a file system—and illustrates them with code snippets and discussions of how the shell, Unix’s command-line user interface, uses them. 本章的其余部分将概述 xv6 的服务——进程、内存、文件描述符、管道和文件系统——并通过代码片段和 shell（Unix 的命令行用户界面）对这些服务的使用来说明它们的设计。shell 对系统调用的使用展示了这些接口是如何被精心设计的。

The shell is an ordinary program that reads commands from the user and executes them. The fact that the shell is a user program, and not part of the kernel, illustrates the power of the system call interface: there is nothing special about the shell. It also means that the shell is easy to replace; as a result, modern Unix systems have a variety of shells to choose from, each with its own user interface and scripting features. The xv6 shell is a simple implementation of the essence of the Unix Bourne shell. Its implementation can be found at (user/sh.c:1).

shell 是一个普通的用户程序，它读取用户输入的命令并执行它们。shell 是用户程序而不是内核的一部分，这体现了系统调用接口的强大之处：shell 本身并没有什么特殊性。这也意味着 shell 很容易被替换；因此，现代 Unix 系统提供了多种不同的 shell，每种都有其独特的用户界面和脚本功能。xv6 的 shell 是对 Unix Bourne shell 精髓的一个简化实现，其源码在 (user/sh.c:1)。

### 1.1 进程与内存

---

**An xv6 process consists of user-space memory (instructions, data, and stack) and per-process state private to the kernel.**
一个 xv6 进程由 **用户空间内存**（指令、数据和栈）以及 **内核中对每个进程私有的状态** 组成。

---

**Xv6 time-shares processes: it transparently switches the available CPUs among the set of processes waiting to execute.**
xv6 通过 **时间共享** 来管理进程：它在等待执行的进程之间透明地切换可用的 CPU。

---

**When a process is not executing, xv6 saves the process’s CPU registers, restoring them when it next runs the process.**
当一个进程没有执行时，xv6 会保存该进程的 CPU 寄存器；当下次运行该进程时，再恢复这些寄存器。

---

**A process may create a new process using the fork system call.**
进程可以通过 **fork 系统调用** 创建一个新进程。

---

**fork gives the new process an exact copy of the calling process’s memory: it copies the instructions, data, and stack of the calling process into the new process’s memory.**

`fork`  会为新进程创建调用进程内存的完全相同副本：它将调用进程的指令段、数据段和栈段全部复制到新进程的内存空间中。


**fork returns in both the original and new processes.**
`fork` 会在原进程和新进程中分别返回。

---

**In the original process, fork returns the new process’s PID. In the new process, fork returns zero.**
在原进程中，`fork` 返回新进程的 **PID**；在新进程中，`fork` 返回 **0**。

---

**The original and new processes are often called the parent and child.**
原进程和新进程通常分别称为 **父进程** 和 **子进程**。

---

**For example, consider the following program fragment written in the C programming language \[7]:**
例如，考虑下面这段用 C 语言编写的程序片段 \[7]：

```c
int pid = fork();
if(pid > 0){
    printf("parent: child=%d\n", pid);
    pid = wait((int *) 0);
    printf("child %d is done\n", pid);
} else if(pid == 0){
    printf("child: exiting\n");
    exit(0);
} else {
    printf("fork error\n");
}
```

---

**The exit system call causes the calling process to stop executing and to release resources such as memory and open files. Exit takes an integer status argument, conventionally 0 to indicate success and 1 to indicate failure.**
`exit` 系统调用会使调用进程停止执行，并释放内存、已打开的文件等资源。`exit` 接受一个整数状态参数，通常 **0 表示成功**，**1 表示失败**。

---

**The wait system call returns the PID of an exited (or killed) child of the current process and copies the exit status of the child to the address passed to wait; if none of the caller’s children has exited, wait waits for one to do so. If the caller has no children, wait immediately returns -1. If the parent doesn’t care about the exit status of a child, it can pass a 0 address to wait.**
`wait` 系统调用返回当前进程中已退出（或被杀死）的子进程的 **PID**，并将子进程的退出状态拷贝到传入的地址中；如果调用者的子进程还没有退出，`wait` 就会等待其中一个退出。如果调用者没有子进程，`wait` 会立即返回 **-1**。如果父进程不关心子进程的退出状态，可以给 `wait` 传递一个 **0 地址**。

---

**In the example, the output lines `parent: child=1234` and `child: exiting` might come out in either order (or even intermixed), depending on whether the parent or child gets to its printf call first.**
在这个例子中，输出的 `parent: child=1234` 和 `child: exiting` 两行可能以任意顺序出现（甚至交错在一起），这取决于父进程和子进程谁先执行到 `printf`。

---

**After the child exits, the parent’s wait returns, causing the parent to print `parent: child 1234 is done`.**
当子进程退出后，父进程的 `wait` 返回，于是父进程打印出 `parent: child 1234 is done`。

---

**Although the child has the same memory contents as the parent initially, the parent and child are executing with separate memory and separate registers: changing a variable in one does not affect the other. For example, when the return value of wait is stored into pid in the parent process, it doesn’t change the variable pid in the child. The value of pid in the child will still be zero.**
尽管子进程一开始与父进程拥有相同的内存内容，但它们运行时各自拥有独立的内存和寄存器：修改其中一个进程的变量不会影响另一个。例如，当 `wait` 的返回值被存入父进程中的 `pid` 变量时，它并不会改变子进程中的 `pid`；子进程中的 `pid` 仍然是 **0**。

---

**The exec system call replaces the calling process’s memory with a new memory image loaded from a file stored in the file system. The file must have a particular format, which specifies which part of the file holds instructions, which part is data, at which instruction to start, etc. Xv6 uses the ELF format, which Chapter 3 discusses in more detail. Usually the file is the result of compiling a program’s source code.**
`exec` 系统调用会用存储在文件系统中的某个文件加载的新内存映像替换调用进程的内存。该文件必须符合特定格式，用来指定文件的哪些部分是指令、哪些部分是数据、从哪条指令开始执行等。xv6 使用 **ELF 格式**，第 3 章会更详细地讨论。通常这个文件是程序源代码编译后的产物。

---

**When exec succeeds, it does not return to the calling program; instead, the instructions loaded from the file start executing at the entry point declared in the ELF header.**
当 `exec` 成功时，它不会返回到调用程序；相反，它会开始执行文件中加载的指令，从 **ELF 头中声明的入口点** 开始运行。

---

**exec takes two arguments: the name of the file containing the executable and an array of string arguments. For example:**
`exec` 接受两个参数：包含可执行文件的文件名，以及一个字符串参数数组。例如：

```c
char *argv[3];
argv[0] = "echo";
argv[1] = "hello";
argv[2] = 0;
exec("/bin/echo", argv);
printf("exec error\n");
```

---

**This fragment replaces the calling program with an instance of the program /bin/echo running with the argument list `echo hello`. Most programs ignore the first element of the argument array, which is conventionally the name of the program.**
这段代码会把调用进程替换为 `/bin/echo` 程序的一个实例，运行时带参数 `echo hello`。大多数程序会忽略参数数组的第一个元素，该元素按照惯例是程序的名字。

---

**The xv6 shell uses the above calls to run programs on behalf of users. The main structure of the shell is simple; see main (user/sh.c:146). The main loop reads a line of input from the user with getcmd. Then it calls fork, which creates a copy of the shell process. The parent calls wait, while the child runs the command.**
xv6 的 shell 使用上述系统调用来代表用户运行程序。shell 的主体结构很简单；见 `main`（user/sh.c:146）。主循环用 `getcmd` 读取用户输入的一行命令，然后调用 `fork`，生成 shell 进程的副本。父进程调用 `wait`，而子进程执行命令。

---

**For example, if the user had typed “echo hello” to the shell, runcmd would have been called with “echo hello” as the argument. runcmd (user/sh.c:55) runs the actual command. For “echo hello”, it would call exec (user/sh.c:79). If exec succeeds then the child will execute instructions from echo instead of runcmd. At some point echo will call exit, which will cause the parent to return from wait in main (user/sh.c:146).**
例如，如果用户在 shell 中输入 “echo hello”，那么 `runcmd` 会以 “echo hello” 作为参数被调用。`runcmd`（user/sh.c:55）运行实际的命令。对于 “echo hello”，它会调用 `exec`（user/sh.c:79）。如果 `exec` 成功，那么子进程就会执行 `echo` 的指令，而不是 `runcmd`。某个时刻，`echo` 会调用 `exit`，这将导致父进程从 `main`（user/sh.c:146）中的 `wait` 返回。

---

**You might wonder why fork and exec are not combined in a single call; we will see later that the shell exploits the separation in its implementation of I/O redirection. To avoid the wastefulness of creating a duplicate process and then immediately replacing it (with exec), operating kernels optimize the implementation of fork for this use case by using virtual memory techniques such as copy-on-write (see Section 4.6).**
你可能会好奇，为什么不把 `fork` 和 `exec` 合并成一次调用；后面我们会看到，shell 在实现 **I/O 重定向** 时正是利用了它们的分离。为了避免先创建一个重复进程、又立刻被 `exec` 替换的低效情况，操作系统内核对 `fork` 的实现进行了优化，采用了诸如 **写时复制（copy-on-write）** 这样的虚拟内存技术（见第 4.6 节）。

---

**Xv6 allocates most user-space memory implicitly: fork allocates the memory required for the child’s copy of the parent’s memory, and exec allocates enough memory to hold the executable file. A process that needs more memory at run-time (perhaps for malloc) can call sbrk(n) to grow its data memory by n zero bytes; sbrk returns the location of the new memory.**
xv6 中大多数用户空间内存是 **隐式分配** 的：`fork` 会分配子进程所需的内存，以复制父进程的内存；`exec` 会分配足够的内存以加载可执行文件。进程如果在运行时需要更多内存（比如用于 `malloc`），可以调用 `sbrk(n)` 来将其数据内存增加 **n 个字节（初始化为 0）**；`sbrk` 返回新内存的位置。

### **1.2 输入/输出与文件描述符**

**A file descriptor is a small integer representing a kernel-managed object that a process may read from or write to.**
文件描述符是一个小整数，用来表示一个由内核管理的对象，进程可以对其进行读写操作。

---

**A process may obtain a file descriptor by opening a file, directory, or device, or by creating a pipe, or by duplicating an existing descriptor.**
进程可以通过 **打开文件、目录或设备**，通过 **创建管道**，或者 **复制现有的文件描述符** 来获得一个新的文件描述符。

**For simplicity we’ll often refer to the object a file descriptor refers to as a “file”; the file descriptor interface abstracts away the differences between files, pipes, and devices, making them all look like streams of bytes. We’ll refer to input and output as I/O.**
为了方便，我们常把文件描述符所指向的对象统称为“文件”；文件描述符接口屏蔽了文件、管道和设备之间的差异，使它们看起来都像是字节流。我们将输入和输出统称为 **I/O**。

**Internally, the xv6 kernel uses the file descriptor as an index into a per-process table, so that every process has a private space of file descriptors starting at zero.**
在内部，xv6 内核把文件描述符作为索引，指向进程私有的文件描述符表，因此每个进程都有一套从 **0 开始**的文件描述符空间。

按照惯例：

* **0** 号文件描述符表示 **标准输入**，
* **1** 号文件描述符表示 **标准输出**，
* **2** 号文件描述符表示 **标准错误**。

正如我们将看到的，shell 正是利用这个约定实现 **I/O 重定向和管道**。shell 确保自己总是打开三个文件描述符（见 user/sh.c:152），它们默认连接到控制台。

**The read and write system calls read bytes from and write bytes to open files named by file descriptors.**
系统调用 `read` 和 `write` 通过文件描述符对已打开的文件进行读写。

**The call `read(fd, buf, n)` reads at most n bytes from the file descriptor fd, copies them into buf, and returns the number of bytes read.**
调用 `read(fd, buf, n)` 会最多从文件描述符 **fd** 中读取 **n** 个字节，拷贝到 **buf** 中，并返回实际读取的字节数。

**Each file descriptor that refers to a file has an offset associated with it.**
每个指向文件的文件描述符都有一个 **偏移量（offset）**。

**read reads data from the current file offset and then advances that offset by the number of bytes read: a subsequent read will return the bytes following the ones returned by the first read. When there are no more bytes to read, read returns zero to indicate the end of the file.**
`read` 会从当前偏移量开始读取数据，然后将偏移量前移已读字节数。下一次调用 `read` 时，会继续读取紧接着的数据。当没有更多数据可读时，`read` 返回 **0**，表示到达文件结尾。

---

**The call `write(fd, buf, n)` writes n bytes from buf to the file descriptor fd and returns the number of bytes written.**
调用 `write(fd, buf, n)` 会把 **buf** 中的 **n** 个字节写入文件描述符 **fd**，并返回实际写入的字节数。

**Fewer than n bytes are written only when an error occurs. Like read, write writes data at the current file offset and then advances that offset by the number of bytes written: each write picks up where the previous one left off.**
只有在发生错误时，写入的字节数才可能少于 **n**。与 `read` 类似，`write` 会在当前文件偏移量处写入数据，然后将偏移量前移写入的字节数：每次写入都会从上一次结束的位置继续。

**The following program fragment (which forms the essence of the program cat) copies data from its standard input to its standard output. If an error occurs, it writes a message to the standard error.**
下面这段程序（它就是 `cat` 程序的核心逻辑）会把数据从标准输入复制到标准输出。如果发生错误，它会将错误信息写到标准错误：

```c
char buf[512];
int n;
for(;;){
    n = read(0, buf, sizeof buf);
    if(n == 0) break;
    if(n < 0){
        fprintf(2, "read error\n");
        exit(1);
    }
    if(write(1, buf, n) != n){
        fprintf(2, "write error\n");
        exit(1);
    }
}
```

**The important thing to note in the code fragment is that cat doesn’t know whether it is reading from a file, console, or a pipe. Similarly cat doesn’t know whether it is printing to a console, a file, or whatever.**
这里需要注意的是，`cat` **并不知道**自己是从文件、控制台还是管道中读取数据。同样，它也**不知道**自己是写到控制台、文件还是其他地方。

**The use of file descriptors and the convention that file descriptor 0 is input and file descriptor 1 is output allows a simple implementation of cat.**
正是因为文件描述符的抽象，以及“**0 表示输入，1 表示输出**”这一约定，`cat` 才能有如此简洁的实现。

**The close system call releases a file descriptor, making it free for reuse by a future open, pipe, or dup system call (see below). A newly allocated file descriptor is always the lowest-numbered unused descriptor of the current process.**
`close` 系统调用会释放一个文件描述符，使其可以被后续的 `open`、`pipe` 或 `dup` 调用重新使用。新分配的文件描述符总是当前进程中 **编号最小的空闲描述符**。

---

**File descriptors and fork interact to make I/O redirection easy to implement. fork copies the parent’s file descriptor table along with its memory, so that the child starts with exactly the same open files as the parent. The system call exec replaces the calling process’s memory but preserves its file table.**
文件描述符与 `fork` 的交互使得 **I/O 重定向** 容易实现。`fork` 会复制父进程的文件描述符表和内存，因此子进程一开始和父进程拥有完全相同的已打开文件。而 `exec` 会替换调用进程的内存映像，但会保留文件描述符表。

**This behavior allows the shell to implement I/O redirection by forking, re-opening chosen file descriptors in the child, and then calling exec to run the new program. Here is a simplified version of the code a shell runs for the command cat < input.txt:**
这种行为使得 shell 能够通过以下方式实现 I/O 重定向：先 `fork` 出子进程，在子进程中重新打开所需的文件描述符，然后调用 `exec` 运行新程序。下面是 shell 运行命令 `cat < input.txt` 的简化代码：

```c
char *argv[2];
argv[0] = "cat";
argv[1] = 0;
if(fork() == 0) {
    close(0);
    open("input.txt", O_RDONLY);
    exec("cat", argv);
}
```

---

**After the child closes file descriptor 0, open is guaranteed to use that file descriptor for the newly opened input.txt: 0 will be the smallest available file descriptor. cat then executes with file descriptor 0 (standard input) referring to input.txt. The parent process’s file descriptors are not changed by this sequence, since it modifies only the child’s descriptors.**
子进程关闭文件描述符 **0** 之后，`open` 保证会把新打开的 `input.txt` 分配为文件描述符 **0**，因为它是最小的空闲描述符。这样 `cat` 在运行时，标准输入就会绑定到 `input.txt`。父进程的文件描述符不会受影响，因为修改只发生在子进程中。

---

**The code for I/O redirection in the xv6 shell works in exactly this way (user/sh.c:83). Recall that at this point in the code the shell has already forked the child shell and that runcmd will call exec to load the new program.**
xv6 的 shell 的 I/O 重定向代码正是这样实现的（见 user/sh.c:83）。注意此时 shell 已经 `fork` 出子进程，接下来 `runcmd` 会调用 `exec` 来加载新程序。

---

**The second argument to open consists of a set of flags, expressed as bits, that control what open does. The possible values are defined in the file control (fcntl) header (kernel/fcntl.h:1-5): O\_RDONLY, O\_WRONLY, O\_RDWR, O\_CREATE, and O\_TRUNC, which instruct open to open the file for reading, or for writing, or for both reading and writing, to create the file if it doesn’t exist, and to truncate the file to zero length.**
`open` 的第二个参数是一组标志位，用二进制位表示，用来控制 `open` 的行为。可能的取值在 **文件控制头文件 fcntl**（kernel/fcntl.h:1-5）中定义，包括：

* `O_RDONLY`：只读打开
* `O_WRONLY`：只写打开
* `O_RDWR`：读写打开
* `O_CREATE`：文件不存在时创建
* `O_TRUNC`：把文件截断为 0 长度

---

**Now it should be clear why it is helpful that fork and exec are separate calls...**
现在可以清楚地看到，为什么 **fork 和 exec 分离** 是有帮助的：在两者之间，shell 有机会在不影响主 shell 的情况下修改子进程的 I/O 设置。

如果有一个假想的 `forkexec` 系统调用，那么 I/O 重定向会变得很麻烦：

* shell 可能需要先修改自己的 I/O 设置，然后再撤销这些修改；
* 或者 `forkexec` 必须接受额外参数来指示 I/O 重定向；
* 又或者（最糟糕的方式）像 `cat` 这样的每个程序都必须自己实现 I/O 重定向。

---

**Although fork copies the file descriptor table, each underlying file offset is shared between parent and child.**
尽管 `fork` 会复制文件描述符表，但其底层的 **文件偏移量在父子进程之间是共享的**。

例如：

```c
if(fork() == 0) {
    write(1, "hello ", 6);
    exit(0);
} else {
    wait(0);
    write(1, "world\n", 6);
}
```

在这段程序运行结束时，附加在 **1 号文件描述符** 上的文件将包含 `hello world`。父进程的写入会从子进程写入结束的位置继续，这种行为有助于保证 **shell 命令序列输出的顺序**（例如 `(echo hello; echo world) > output.txt`）。

---

**The dup system call duplicates an existing file descriptor, returning a new one that refers to the same underlying I/O object. Both file descriptors share an offset, just as the file descriptors duplicated by fork do.**
`dup` 系统调用会复制一个已有的文件描述符，返回一个新的文件描述符，指向相同的底层 I/O 对象。它们共享偏移量，就像通过 `fork` 复制的描述符一样。

例如：

```c
fd = dup(1);
write(1, "hello ", 6);
write(fd, "world\n", 6);
```

---

**Two file descriptors share an offset if they were derived from the same original file descriptor by a sequence of fork and dup calls. Otherwise file descriptors do not share offsets, even if they resulted from open calls for the same file.**
两个文件描述符只有在通过一系列 `fork` 和 `dup` 调用从同一个原始文件描述符派生出来时才会共享偏移量。否则，即使它们是分别通过 `open` 打开的同一个文件，它们的偏移量也不共享。

---

**dup allows shells to implement commands like this: `ls existing-file non-existing-file > tmp1 2>&1`.**
`dup` 使得 shell 能够实现如下命令：

```bash
ls existing-file non-existing-file > tmp1 2>&1
```

这里 `2>&1` 告诉 shell：把文件描述符 **2（标准错误）** 设置为 **1（标准输出）** 的副本。这样，存在文件的名字和不存在文件的错误消息都会输出到 `tmp1`。

---

**The xv6 shell doesn’t support I/O redirection for the error file descriptor, but now you know how to implement it.**
xv6 的 shell 并不支持对错误输出的重定向，但现在你已经知道该怎么实现它了。

---

**File descriptors are a powerful abstraction, because they hide the details of what they are connected to: a process writing to file descriptor 1 may be writing to a file, to a device like the console, or to a pipe.**
文件描述符是一种非常强大的抽象，因为它们屏蔽了底层连接对象的细节：进程向 **1 号文件描述符** 写入时，它可能是写到文件、写到控制台设备，或者写到管道。

---

### **1.3 管道（Pipes）**

**A pipe is a small kernel buffer exposed to processes as a pair of file descriptors, one for reading and one for writing.**
管道是内核中的一个小缓冲区，它以一对文件描述符的形式暴露给进程：一个用于读取，一个用于写入。

**Writing data to one end of the pipe makes that data available for reading from the other end of the pipe. Pipes provide a way for processes to communicate.**
当数据写入管道的一端时，另一端就可以读取到这些数据。管道为进程之间提供了一种通信机制。

---

**The following example code runs the program wc with standard input connected to the read end of a pipe.**
下面的示例代码运行 `wc` 程序，并将它的标准输入连接到管道的读端：

```c
int p[2];
char *argv[2];
argv[0] = "wc";
argv[1] = 0;
pipe(p);
if(fork() == 0) {
    close(0);
    dup(p[0]);
    close(p[0]);
    close(p[1]);
    exec("/bin/wc", argv);
} else {
    close(p[0]);
    write(p[1], "hello world\n", 12);
    close(p[1]);
}
```

---

**The program calls pipe, which creates a new pipe and records the read and write file descriptors in the array p.**
程序调用 `pipe`，它会创建一个新管道，并把读端和写端的文件描述符存入数组 `p` 中。

**After fork, both parent and child have file descriptors referring to the pipe.**
`fork` 之后，父进程和子进程都拥有指向管道的文件描述符。

**The child calls close and dup to make file descriptor zero refer to the read end of the pipe, closes the file descriptors in p, and calls exec to run wc. When wc reads from its standard input, it reads from the pipe.**
子进程通过 `close` 和 `dup` 让文件描述符 **0**（标准输入）指向管道的读端，接着关闭 `p` 中的文件描述符，再调用 `exec` 执行 `wc`。这样，当 `wc` 从标准输入读取时，实际上就是在从管道读取。

**The parent closes the read side of the pipe, writes to the pipe, and then closes the write side.**
父进程关闭管道的读端，向管道写入数据，然后再关闭写端。

---

**If no data is available, a read on a pipe waits for either data to be written or for all file descriptors referring to the write end to be closed; in the latter case, read will return 0, just as if the end of a data file had been reached.**
如果管道中没有数据，`read` 会阻塞，直到有数据写入，或者直到所有指向管道写端的文件描述符都被关闭；在后一种情况下，`read` 返回 **0**，就像到达文件结尾一样。

**The fact that read blocks until it is impossible for new data to arrive is one reason that it’s important for the child to close the write end of the pipe before executing wc above: if one of wc’s file descriptors referred to the write end of the pipe, wc would never see end-of-file.**
由于 `read` 会一直阻塞，直到不可能再有新数据到来，因此在上面的例子中，子进程在执行 `wc` 前关闭写端是至关重要的。如果 `wc` 还持有指向写端的描述符，它将永远不会看到文件结束标志。

---

**The xv6 shell implements pipelines such as `grep fork sh.c | wc -l` in a manner similar to the above code (user/sh.c:101).**
xv6 的 shell 用类似的方法实现了管道。例如：

```bash
grep fork sh.c | wc -l
```

（见 user/sh.c:101）。

**The child process creates a pipe to connect the left end of the pipeline with the right end. Then it calls fork and runcmd for the left end of the pipeline and fork and runcmd for the right end, and waits for both to finish.**
子进程创建一个管道，把流水线左端和右端连接起来。然后它对左端调用 `fork` 和 `runcmd`，再对右端调用 `fork` 和 `runcmd`，最后等待两边都执行完。

**The right end of the pipeline may be a command that itself includes a pipe (e.g., `a | b | c`), which itself forks two new child processes (one for b and one for c). Thus, the shell may create a tree of processes. The leaves of this tree are commands and the interior nodes are processes that wait until the left and right children complete.**
流水线的右端可能本身也包含管道（例如 `a | b | c`），这会再产生两个子进程（一个运行 `b`，一个运行 `c`）。因此，shell 可能会生成一棵 **进程树**：叶子节点是具体的命令，而中间节点则是等待左右子进程完成的进程。

---

**Pipes may seem no more powerful than temporary files...**
乍一看，管道似乎并不比临时文件更强大。例如：

```bash
echo hello world | wc
```

完全可以改写为：

```bash
echo hello world >/tmp/xyz; wc </tmp/xyz
```

---

**Pipes have at least three advantages over temporary files in this situation.**
但在这种情况下，管道至少有三个优势：

1. **自动清理**：管道会在使用结束后自动清理；而临时文件则需要 shell 负责删除 `/tmp/xyz`。
2. **无限数据流**：管道可以传输任意长度的数据流；而临时文件则需要足够的磁盘空间来存放全部数据。
3. **并行执行**：管道允许流水线各阶段并行运行；而临时文件方式必须等待前一个程序运行完毕，后一个程序才能开始。

---

### **1.4 文件系统**

**The xv6 file system provides data files, which contain uninterpreted byte arrays, and directories, which contain named references to data files and other directories.**
xv6 的文件系统提供两类基本对象：

* **数据文件**：存放未经解释的字节数组；
* **目录**：包含对数据文件和其他目录的命名引用。

---

**The directories form a tree, starting at a special directory called the root. A path like `/a/b/c` refers to the file or directory named `c` inside the directory named `b` inside the directory named `a` in the root directory `/`.**
目录形成了一棵树，从一个特殊的目录 **根目录（root）** 开始。像 `/a/b/c` 这样的路径，表示根目录 `/` 下的 `a` 目录中的 `b` 目录中的 `c` 文件或目录。

**Paths that don’t begin with `/` are evaluated relative to the calling process’s current directory, which can be changed with the `chdir` system call.**
不以 `/` 开头的路径会相对于调用进程的 **当前工作目录** 来解析，而当前目录可以通过 `chdir` 系统调用来修改。

---

**Both these code fragments open the same file (assuming all the directories involved exist):**
下面两段代码打开的是同一个文件（假设目录都存在）：

```c
chdir("/a");
chdir("b");
open("c", O_RDONLY);

open("/a/b/c", O_RDONLY);
```

**The first fragment changes the process’s current directory to `/a/b`; the second neither refers to nor changes the process’s current directory.**
第一段代码把进程的当前目录改成了 `/a/b`；第二段代码则既没有引用也没有修改当前目录。

---

**There are system calls to create new files and directories: `mkdir` creates a new directory, `open` with the `O_CREATE` flag creates a new data file, and `mknod` creates a new device file. This example illustrates all three:**
有系统调用可以创建新文件和目录：

* `mkdir`：创建一个新目录；
* `open`（带 `O_CREATE` 标志）：创建一个新的数据文件；
* `mknod`：创建一个新的设备文件。

例如：

```c
mkdir("/dir");
fd = open("/dir/file", O_CREATE|O_WRONLY);
close(fd);
mknod("/console", 1, 1);
```

---

**mknod creates a special file that refers to a device. Associated with a device file are the major and minor device numbers (the two arguments to mknod), which uniquely identify a kernel device.**
`mknod` 创建的是一个特殊文件，它对应某个设备。设备文件会关联 **主设备号** 和 **次设备号**（`mknod` 的两个参数），它们用来唯一标识内核中的设备。

**When a process later opens a device file, the kernel diverts read and write system calls to the kernel device implementation instead of passing them to the file system.**
当进程之后打开设备文件时，内核会把 `read` 和 `write` 系统调用转发给设备的实现，而不是交给文件系统处理。

---

**A file’s name is distinct from the file itself; the same underlying file, called an inode, can have multiple names, called links.**
文件的 **名字** 和文件本身是不同的。一个底层文件（称为 **inode**）可以有多个名字，这些名字叫做 **链接（links）**。

**Each link consists of an entry in a directory; the entry contains a file name and a reference to an inode.**
每个链接是目录中的一项，它包含一个文件名和一个指向 inode 的引用。

**An inode holds metadata about a file, including its type (file, directory, or device), its length, the location of the file’s content on disk, and the number of links to a file.**
inode 保存了文件的 **元数据**，包括：文件类型（普通文件、目录或设备）、文件长度、磁盘上内容的位置，以及指向该文件的链接数量。

---

**The `fstat` system call retrieves information from the inode that a file descriptor refers to. It fills in a `struct stat`, defined in `stat.h` (kernel/stat.h) as:**
`fstat` 系统调用用于获取文件描述符所指向的 inode 的信息，并填充到 `struct stat` 中。其定义在 `stat.h`（kernel/stat.h）中：

```c
#define T_DIR 1    // 目录
#define T_FILE 2   // 普通文件
#define T_DEVICE 3 // 设备

struct stat {
    int dev;      // 文件系统所在的磁盘设备
    uint ino;     // inode 编号
    short type;   // 文件类型
    short nlink;  // 指向该文件的链接数
    uint64 size;  // 文件大小（字节）
};
```

---

**The `link` system call creates another file system name referring to the same inode as an existing file. This fragment creates a new file named both `a` and `b`.**
`link` 系统调用可以为已有文件创建一个新的名字，指向同一个 inode。下面的代码会创建两个文件名 `a` 和 `b`，它们实际上指向同一个文件：

```c
open("a", O_CREATE|O_WRONLY);
link("a", "b");
```

**Reading from or writing to `a` is the same as reading from or writing to `b`.**
对 `a` 的读写和对 `b` 的读写效果完全相同。

**After the code sequence above, it is possible to determine that `a` and `b` refer to the same underlying contents by inspecting the result of fstat: both will return the same inode number (ino), and the nlink count will be set to 2.**
执行上述代码后，可以通过 `fstat` 来确认 `a` 和 `b` 指向同一个文件：它们会返回相同的 inode 编号，并且 `nlink` 数为 2。

---

**The `unlink` system call removes a name from the file system.**
`unlink` 系统调用会从文件系统中移除一个名字。

**The file’s inode and the disk space holding its content are only freed when the file’s link count is zero and no file descriptors refer to it.**
只有当文件的链接数为 **0** 且没有文件描述符再引用它时，该文件的 inode 和磁盘空间才会被释放。

例如：

```c
unlink("a");
```

会让文件内容依旧通过 `b` 可访问。

再比如：

```c
fd = open("/tmp/xyz", O_CREATE|O_RDWR);
unlink("/tmp/xyz");
```

这种写法会创建一个 **没有名字的临时文件**，它会在进程关闭 `fd` 或退出时自动清理。

---

**Unix provides file utilities callable from the shell as user-level programs, for example mkdir, ln, and rm.**
Unix 提供了一些文件工具，以用户态程序的形式可以从 shell 调用，比如 `mkdir`、`ln` 和 `rm`。

**This design allows anyone to extend the command-line interface by adding new user-level programs.**
这种设计使得任何人都可以通过增加新的用户态程序来扩展命令行功能。

**In hindsight this plan seems obvious, but other systems designed at the time of Unix often built such commands into the shell (and built the shell into the kernel).**
回过头来看，这种设计似乎理所当然，但在 Unix 诞生的年代，其他系统往往把这些命令直接写进 shell（甚至写进内核）。

---

**One exception is cd, which is built into the shell (user/sh.c:161).**
有一个例外是 `cd`，它必须内置在 shell 里（见 user/sh.c:161）。

**cd must change the current working directory of the shell itself.**
`cd` 必须改变 shell 自身的当前工作目录。

**If cd were run as a regular command, then the shell would fork a child process, the child process would run cd, and cd would change the child’s working directory. The parent’s (i.e., the shell’s) working directory would not change.**
如果把 `cd` 当作普通命令运行，那么 shell 会 `fork` 出一个子进程，子进程运行 `cd` 并修改它自己的工作目录，而父进程（即 shell）的工作目录不会改变。

---

### **1.5 现实世界**

**Unix’s combination of “standard” file descriptors, pipes, and convenient shell syntax for operations on them was a major advance in writing general-purpose reusable programs.**
Unix 把“标准文件描述符”、管道以及对它们操作的简洁 shell 语法结合起来，这在编写通用、可复用的程序方面是一个巨大的进步。

---

**The idea sparked a culture of “software tools” that was responsible for much of Unix’s power and popularity, and the shell was the first so-called “scripting language.”**
这一思想催生了“软件工具”文化，它成为 Unix 强大功能和广泛流行的重要原因。而 shell 则是最早的所谓“脚本语言”。

---

**The Unix system call interface persists today in systems like BSD, Linux, and macOS.**
Unix 的系统调用接口一直延续至今，存在于 BSD、Linux 和 macOS 等系统中。

---

**The Unix system call interface has been standardized through the Portable Operating System Interface (POSIX) standard.**
Unix 的系统调用接口已通过 **可移植操作系统接口（POSIX）** 标准实现了规范化。

**Xv6 is not POSIX compliant: it is missing many system calls (including basic ones such as lseek), and many of the system calls it does provide differ from the standard.**
不过，xv6 并不符合 POSIX 标准：它缺少许多系统调用（甚至包括像 `lseek` 这样最基本的调用），而且它所提供的一些调用与标准并不完全一致。

**Our main goals for xv6 are simplicity and clarity while providing a simple UNIX-like system-call interface.**
xv6 的主要目标是 **简洁和清晰**，同时提供一个简单的、类 Unix 的系统调用接口。

---

**Several people have extended xv6 with a few more system calls and a simple C library in order to run basic Unix programs.**
一些人对 xv6 进行了扩展，增加了一些系统调用和一个简易的 C 库，以便能够运行基本的 Unix 程序。

**Modern kernels, however, provide many more system calls, and many more kinds of kernel services, than xv6.**
然而，现代内核提供的系统调用和内核服务远比 xv6 丰富。

**For example, they support networking, windowing systems, user-level threads, drivers for many devices, and so on.**
例如，它们支持网络、窗口系统、用户态线程、各种设备的驱动程序，等等。

**Modern kernels evolve continuously and rapidly, and offer many features beyond POSIX.**
现代内核在不断快速演进，提供了远超 POSIX 的功能。

---

**Unix unified access to multiple types of resources (files, directories, and devices) with a single set of file-name and file-descriptor interfaces.**
Unix 用一套统一的 **文件名** 和 **文件描述符** 接口实现了对多种资源（文件、目录和设备）的统一访问。

**This idea can be extended to more kinds of resources; a good example is Plan 9 \[16], which applied the “resources are files” concept to networks, graphics, and more.**
这一思想还可以扩展到更多类型的资源。一个很好的例子是 **Plan 9** \[16]，它把“资源即文件”的理念应用到了网络、图形等领域。

**However, most Unix-derived operating systems have not followed this route.**
不过，大多数 Unix 衍生操作系统并没有走这条路。

---

**The file system and file descriptors have been powerful abstractions. Even so, there are other models for operating system interfaces.**
文件系统和文件描述符是一种非常强大的抽象。然而，操作系统接口还有其他模型。

**Multics, a predecessor of Unix, abstracted file storage in a way that made it look like memory, producing a very different flavor of interface.**
Unix 的前身 **Multics** 就把文件存储抽象成类似内存的形式，从而形成了一种完全不同风格的接口。

**The complexity of the Multics design had a direct influence on the designers of Unix, who aimed to build something simpler.**
Multics 的复杂设计直接影响了 Unix 的设计者，使他们的目标转向构建一个更简单的系统。

---

**Xv6 does not provide a notion of users or of protecting one user from another; in Unix terms, all xv6 processes run as root.**
xv6 并没有用户的概念，也没有实现用户之间的隔离；用 Unix 的说法，所有 xv6 进程都以 **root** 身份运行。

---

**This book examines how xv6 implements its Unix-like interface, but the ideas and concepts apply to more than just Unix.**
本书探讨的是 xv6 如何实现它的类 Unix 接口，但这些思想和概念不仅仅适用于 Unix。

**Any operating system must multiplex processes onto the underlying hardware, isolate processes from each other, and provide mechanisms for controlled inter-process communication.**
任何操作系统都必须做到以下几点：

* 将多个进程复用到底层硬件上，
* 在进程间实现隔离，
* 提供可控的进程间通信机制。

**After studying xv6, you should be able to look at other, more complex operating systems and see the concepts underlying xv6 in those systems as well.**
学习过 xv6 之后，你应该能够在其他更复杂的操作系统中，识别出那些同样存在的核心概念。

**1. Write a program that uses UNIX system calls to “ping-pong” a byte between two processes over a pair of pipes, one for each direction. Measure the program’s performance, in exchanges per second.**

1. 编写一个程序，利用 **UNIX 系统调用** 在两个进程之间通过一对管道（每个方向一个管道）来“乒乓”传递一个字节。测量该程序的性能，以**每秒交换次数**来表示。
